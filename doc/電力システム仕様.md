# City-Sim 電力システム仕様

## 1. 位置付け

対象: v1.0.15。最終的な正は現行ソースコード。本書は `src/power/` と関連runtime tuningの現行仕様をまとめる。

実装済み: Phase 1〜10、Phase 12。Phase 11（電力オーバーレイ）は未実装。

v1.0.15ではライフライン職場の優先人員配置・24時間交代勤務と、火力発電所の燃料在庫/実車両補給を追加した。

## 2. 全体構成

`PowerSystem` が発電、外部受電、地下電力線、変電所、建物/インフラ負荷、優先給電、停電を管理する。道路Edgeを地下電力線の論理経路として再利用し、通常時は電力線を描画しない。

主な実装:

- `PowerSystem.ts`: 系統構築、需給、配電、停電、snapshot
- `PowerTypes.ts`: 型、状態、設定、単位
- `PowerDemandModel.ts`: 建物/POI需要
- `PowerQualityModel.ts`: P/Q、電圧、周波数、位相、三相近似
- `PowerIntegration.ts`: World統合、ライフライン施設初期化
- `PowerLifelineRuntime.ts`: 発電所Work POI登録
- `PowerLifelineOperations.ts`: 発電出力への人員/燃料制約、snapshot
- `GenerationFuelModel.ts`: 火力燃料在庫、発注点、輸送中予約、消費
- `LifelineSupplyIntegration.ts`: 市内/外部からの実車両燃料輸送
- `PowerOperationalIntegration.ts`: 生産/交通/照明等への影響
- `PowerPerformanceTuning.ts`: キャッシュ、需要周期、性能計測
- `PowerRuntimeRegistry.ts`: runtime参照
- `PowerUiTuning.ts`: F10電力UI、Inspector拡張
- `LifelineWorkforce.ts`: 将来の水道/下水/通信等にも再利用するライフライン職場レジストリ

## 3. 単位と状態

内部電力は原則kW、UI/集計はMWを使用する。`1 MW = 1000 kW`。

系統状態:

- `normal`: 正常
- `tight`: 逼迫
- `limited-supply`: 制限給電
- `blackout`: 停電

需要家状態は `supplied / limited / blackout / disconnected`。設備は `online / standby / offline / fault`、線路は `active / broken`。

## 4. 発電・外部受電

標準設定は火力2基×350 MW、太陽光3基×90 MW、外部系統2接続×600 MW。太陽光は時刻で出力が変動する。発電所と外部接続点は最寄り道路ノードへ接続される。

v1.0.15以降、発電所の利用可能出力は定格/日射だけでなく、勤務中人員と火力燃料在庫にも制約される。

```text
利用可能出力
= 従来の利用可能出力
× 人員充足係数
× 燃料係数（火力のみ）
```

## 5. ライフライン職場・24時間勤務

`LifelineWorkforce` は電力だけに依存しない共通レジストリ。将来、水道、下水、通信、ガス等を同じ方式で登録できる。

発電所はPowerSystem生成直後かつ住民 `populate()` より前にWork POIとして登録する。このため通常の職場割当と同じAgentを使いながら、職場割当時にはライフラインとして特別扱いできる。

### 5.1 優先配置

通常職場は既存仕様通り概ねcapacityの50%を最低保証目標とする。ライフライン職場はロスター100%を目標とし、欠員処理順も通常職場より前にする。

自然生成の労働者だけで不足する場合は、住宅/AgentStore容量の範囲で追加の就業住民を生成する。ライフラインの欠員は通常職場の欠員とは分けて診断ログへ出す。

### 5.2 3交代

発電所は以下の3交代を基本とする。

```text
早番 06:00-14:00
遅番 14:00-22:00
夜勤 22:00-06:00
```

ロスターは `同時勤務目標 × 3 × lifelineRosterReliefRatio` を基礎とし、各Agentを3シフトへ均等配分する。標準 `lifelineRosterReliefRatio=1.15` は休日/交代余裕を表す。

標準同時勤務人数は発電容量に比例し、火力は100 MWあたり4.5人（最低8人）、太陽光は100 MWあたり1.5人（最低2人）。実際に職場へ到着して `Engaged` 中の人数を同時勤務目標で割り、人員係数を求める。

## 6. 火力燃料・在庫

火力発電所は抽象化した `thermal-fuel` 在庫を持つ。燃料は無限供給ではなく、実発電量に応じて消費する。

標準値:

- 消費係数: 0.18 fuel units / MWh
- 貯蔵: 最大出力換算96時間
- 初期在庫: 貯蔵量の80%
- 通常補給開始: 残60時間
- 緊急補給: 残18時間
- 補給目標: 貯蔵量の90%

在庫0では火力の利用可能出力は0になる。次回配電周期を満たす燃料が不足する場合は、その周期で発電可能な割合まで出力を制限する。

燃料Snapshotは現在在庫、容量、輸送中予約、残運転時間、状態、総受入量、市内/外部別受入量を保持する。

## 7. 燃料調達・実車両物流

燃料補給は `LifelineSupplyIntegration` が既存 `LogisticsSystem` / `TrafficSystem` / `VehicleStore` を使って実車両で行う。

### 7.1 発注

`stock + reservedInbound` がreorder point以下になると発注対象になる。輸送中の積載量を `reservedInbound` として数えるため、同一需要に対する重複発注を抑制する。

緊急/空在庫の発電所、残運転時間が短い発電所を先に処理する。

### 7.2 市内調達

既存産業サプライチェーンの `raw-factory` を燃料供給候補として使う。ただし工場の全在庫を電力側が奪わないよう、`thermalFuelInternalReserveRatio` 分の在庫を工場側へ残す。

市内余剰があれば発電所に近いraw-factoryから予約し、実際の燃料輸送Truckが以下を走る。

```text
freight depot
→ raw-factory
→ loading
→ thermal plant
→ unloading
→ freight depot
```

### 7.3 外部輸入

市内raw-factoryに十分な余剰がない場合、最寄りの都市外gateを供給元にする。

```text
freight depot
→ city gate
→ loading
→ thermal plant
→ unloading
→ freight depot
```

外部輸入も数値を直接加算せず、Truckが到着して荷下ろしを完了した時点で在庫へ加える。

標準燃料車fleetは最大10台、積載180 units/台。VehicleStore上では専用truck ID帯を使い、通常貨物fleetとは独立したphase/cargo APIを持つ。

## 8. 地下電力網・変電所

道路Edgeを `PowerLineSegment` に対応させる。区間ごとに容量、現在負荷、有効/断線、過負荷、Power Zoneを保持する。

標準線路容量:

| 道路 | 容量 |
|---|---:|
| Highway | 260 MW |
| Arterial | 180 MW |
| Collector | 110 MW |
| Local | 55 MW |
| Path | 12 MW |

変電所は標準1,800 m間隔、75 MW/基、サービス半径2,600 m。発電源→変電所→需要家の到達性と経路容量を評価する。断線等でtopologyが変化した場合だけ再構築する。

## 9. 建物・インフラ接続

建物IDは変更せずside dataとして電力接続を保持する。主な値は需要、給電量、給電率、接続変電所、優先度、状態、Power Zone、配電経路。

非建物負荷として道路信号、街灯、鉄道信号、駅、鉄道牽引を扱う。

## 10. 需要モデル

基本形:

```text
需要 = 基本需要 × 建物規模 × 稼働率 × 時間帯係数
```

住宅、オフィス、商業、工場、物流、ホテル、病院、大学/学校、公共施設を用途別に扱い、POI capacity/occupancyも反映する。通常の系統更新は5 simulation秒、需要再計算は標準15 simulation秒。

`demandUpdateIntervalSec` はv1.0.15で正式な `PowerConfig` / Loader検証項目になった。

## 11. 系統計算と局所不足

Power Zone単位で発電/外部受電、需要、供給、予備力を集計する。供給可能量はゾーン電源容量、変電所容量、共有幹線容量、需要家までの経路容量に制約される。

このため都市全体に余力があっても、断線、変電所容量超過、地域幹線過負荷により局所的な制限給電/停電が発生する。

## 12. 優先給電・非常電源

優先順位:

1. Critical: 病院、警察、消防、道路信号、鉄道信号
2. High: 駅、学校/大学、公共施設、鉄道運行
3. Medium: 工場、物流、商業、オフィス、ホテル等
4. Low: 住宅、街灯等

不足時は上位から容量を割り当てる。給電率は0〜1で保持する。Critical負荷には標準35%の非常電源枠を持たせ、信号系は停電が交通デッドロックを直接誘発しにくい安全側の挙動とする。

## 13. 電力品質モデル

50 Hz、22 kV系統、400 V需要家を標準とする。これは厳密なNewton-Raphson AC潮流ではなく、大規模都市向けの線形化近似モデル。

- 有効電力P、無効電力Q、皮相電力S、力率を扱う
- `Q = P × tan(acos(PF))`
- 三相基準位相: A=0°、B=-120°、C=+120°
- 大規模負荷はABC、小規模負荷はA/B/Cへ分散
- 相別電流、電圧、相不平衡率を計算
- 線路長とR/Xから電圧降下・位相差を近似
- 需給不足からdroop近似で周波数偏差を算出

標準線路定数は R=0.18 Ω/km、X=0.11 Ω/km。

## 14. シミュレーションへの影響

給電率と電力品質は工場/物流の生産、オフィス等の稼働、商業POIの実効能力、夜間建物照明、街灯、駅照明へ反映する。鉄道は軽微な不足では維持し、牽引電力品質が深刻に低下した場合のみ速度制限する。信号は優先給電/非常電源で可能な限り維持する。

発電側もv1.0.15から勤務中人員と燃料在庫に依存するため、人手不足や道路物流障害が供給力低下へ波及する。

## 15. UI

F10全画面メニューに「電力」を追加済み。都市全体の需要、供給、市内発電、外部受電、予備力/予備率、状態、停電数に加え、発電所、変電所、Power Zone、過負荷/断線区間を確認できる。

建物Inspectorでは需要、給電量、給電率、接続変電所、優先度、状態、電圧、周波数、力率、相を表示する。

Phase 11の地下幹線/停電地域オーバーレイは未実装であり、通常時の追加描画負荷はない。

## 16. 性能・安定性

- topology変更時のみ系統再構築
- Consumer一覧をキャッシュ
- 結合済み送電経路をキャッシュ
- 需要計算を配電更新から分離
- `powerPerformanceSnapshot()` で更新/配電/需要/topology時間と回数を取得
- CIで102,000 Consumer相当のストレスベンチを実行
- 断線→復旧、発電不足→正常復帰、seed差分を自動検証
- `feat/**` branchもpush時にbuild CIを実行

P12導入時のCI synthetic benchmarkでは対象ホットパスが271.86 ms→137.43 ms（約1.98倍）だった。これはゲーム全体FPSの倍率ではない。

## 17. 主なSnapshot/API

- `powerSnapshot()`

- Power Zone snapshot
- `powerQualitySnapshot()` と電気量snapshot
- `powerPerformanceSnapshot()`

## 18. 未実装・非対象

未実装: Phase 11電力オーバーレイ。

現行近似モデルで扱わないもの: 厳密AC潮流、詳細なケーブル電気特性、厳密な送電損失、電気料金/電力市場。電柱、架空線、通常時の電線レンダリングも実装しない。

火力燃料は現在抽象fuel unitであり、石炭/重油/LNG等の燃料種別ごとの物性・専用設備差は未分化。今後必要になれば共通供給モデル上でmaterial種別を追加する。

## 19. 変更時チェック

電力ロジック変更時は本書、`現行仕様書.md`、必要に応じて`基本設計書.md`/`詳細設計書.md`を更新する。`power`設定変更時は`設定ファイル仕様.md`も同期し、性能挙動変更時はP12 benchmarkとCIを確認する。
