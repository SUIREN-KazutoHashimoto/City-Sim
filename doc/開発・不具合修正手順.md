# City-Sim 開発・不具合修正手順

> Target: `develop` / synchronized at v1.0.30 / 2026-08-27. **現行repository rulesとソースコードを正とする。**

この文書は新機能、性能改善、文書整備、不具合修正の標準フローを定める。

## 1. 基本原則

1. 作業は原則`develop`の最新から開始する。
2. 変更前に現行コードと最終runtime patchを読む。
3. 症状と原因を分ける。不具合は原因を説明してから修正する。
4. 変更範囲を小さく保つが、本来コアを直すべき問題までpatchで隠さない。
5. **developへ残る変更バッチ/コミットごとに`APP_VERSION`を上げる。** docs-onlyも例外にしない。
6. TypeScript安全性を全体で弱めない。
7. CI成功とブラウザ実機確認を別物として扱う。
8. 既存挙動を変える場合は「維持する契約」と「変更する契約」を明示する。
9. PRに未確認事項を書く。実機未確認を確認済みと表現しない。
10. 現行仕様を変えたら該当documentを同じ作業で同期する。

## 2. Branch / repository rules

標準branch:

| 種別 | 例 |
|---|---|
| feature | `feat/fullscreen-menu` |
| fix | `fix/intersection-deadlock` |
| performance | `perf/agent-rendering` |
| docs | `docs/v1.0.30-sync` |

基本フロー:

```text
develop latest
  ↓
feat / fix / perf / docs branch
  ↓
implementation + validation
  ↓
PR → develop
  ↓
required build check
  ↓
merge
```

### 2.1 develop protection

現行repository rulesでは`develop`への通常の直接writeは拒否される。

Required behavior:

- changes must be made through a Pull Request;
- required status check `build` must pass.

「developへ直接コミットして」と依頼された場合でも、repository protectionを解除・迂回しない。最小branch/PRを作成し、required checkを通してmergeし、最終結果としてdevelopを更新する。

`main`はrelease系統。通常開発から直接更新しない。`release/*`はrelease preparation用途として扱い、通常feature branchの代替にしない。

## 3. Version運用

`src/version.ts`の`APP_VERSION`を更新する。

- feature/fix/perf/docsを含め、developへ残る変更単位でversionを上げる。
- PR上で複数の作業commitを作った場合でも、最終merge historyを意図した単位へ整理する。
- CI修正など別の意味を持つ追加変更をdevelopへ別commitとして残すなら、さらにversionを上げる。
- `version.ts`はruntime tuning import entryでもあるため、version文字列以外を触る場合はimport順を再確認する。

## 4. 新機能の標準手順

### 4.1 要求を分解

- 外から見えるbehavior
- state/data owner
- simulation update
- rendering/UI
- Inspector/list/jump
- config
- persistence
- performance
- existing integration
- documentation

UI要求でもsnapshot/APIが必要な場合がある。逆にsimulation変更でも既存stateの可視化だけなら新stateを増やさない。

### 4.2 実効code pathを確認

特に確認:

- state owner
- update loop
- later runtime override
- `src/version.ts` import order
- worker/shared state mirror
- UIが別の集計を持っていないか
- logical entityとrender entityが同じか

### 4.3 実装方式を選ぶ

Runtime patchが向く:

- 小さな既存behavior補正
- regression scopeを局所化
- UI/Inspector追加
- 比較・rollbackしやすくしたい

Core変更が向く:

- class自身のinvariantが壊れている
- 全callerで同じ修正が必要
- hot pathでwrapper overheadが不要
- 同責務patchが世代重複している
- data ownershipを変える必要がある

### 4.4 実装時の一般invariant

- Agent/Vehicle/Building/POI IDを途中で不必要に詰め直さない
- TypedArray capacityを超えない
- reserveしたPOI/parking等はfailure pathでrelease
- rendering coordinateとsimulation coordinateを混同しない
- logical entityと別のvisual entityを二重生成しない
- patch install guardを置く
- `previous` wrapper chainとreturn valueを維持する

## 5. 不具合修正の手順

修正前に最低限記録:

```text
症状:
期待:
実際:
再現条件:
頻度:
影響範囲:
version / branch:
```

その後:

1. 実効code pathを追う。
2. 一文で原因を説明できる状態にする。
3. 原因を持つ最小責務へ修正を置く。
4. 元の再現条件で症状が消えたか確認する。
5. 反対側/近接する正常caseが壊れていないか確認する。
6. 必要ならコメント/文書へ「なぜ」を残す。

Timeout/force recoveryはsimulation保護として有効な場合があるが、根本原因が別にある場合はrecoveryだけを最終修正にしない。

## 6. Runtime patch実装ルール

典型:

```ts
const proto = Target.prototype as unknown as Record<string, any>;
if (!proto.__citySimExamplePatchVNNN) {
  const previous = proto.method as (...args: any[]) => any;
  proto.method = function patched(this: Record<string, any>, ...args: any[]) {
    const result = previous.apply(this, args);
    return result;
  };
  proto.__citySimExamplePatchVNNN = true;
}
```

ルール:

- install guard必須
- previous chain維持
- before/after順を意図的に決める
- return値を失わない
- private access用`any`/`Record<string, any>`はpatch境界へ限定
- compiler全体を緩めない
- HMR時のwrapper stackを考慮し、必要ならhard reloadを検証手順へ書く

## 7. Build / CI

Local最低確認:

```bash
npm ci
npm run build
npm run bench:power
```

GitHub Actions `build` job:

1. Node 24
2. `npm ci`
3. TypeScript + Vite build
4. Power P12 stress benchmark
5. `dist/LICENSE`
6. `dist/NOTICE`
7. `dist/THIRD_PARTY_NOTICES.txt`
8. third-party notice content verification

`build` successはbrowser behaviorの正しさを保証しない。

Workflow push triggerはbranch patternごとに異なるが、develop向けPRではrequired `build` checkが走る。Push trigger対象外branchでもPRを開いてrequired checkを通す。

## 8. 実機確認

変更pathを最低1回通す。

Examples:

- UI: open/close、search、paging、保存、reload、jump
- Vehicle: spawn、run、intersection、arrival、redispatch
- Rail: straight/curve/station/turnback/night
- Agent: walk/bus/rail/taxi/work/activity
- Power: demand/supply、staffing、fuel、fault/recovery、facility jump
- Generation: multiple seeds、center/outskirts、capacity/reservation conflict

CIだけでは確認できない場合、PRへ「実機確認が必要」と明記する。

## 9. PR本文

最低限:

- 目的
- 原因（bugfixの場合）
- 実装内容
- 重要な数値/semantic変更
- CI結果
- 実機確認結果
- 未確認事項
- 既知制約
- 文書更新範囲

Merge前にbaseが最新か、conflict/required checksを確認する。

## 10. Documentation workflow

仕様変更時は、まず実装を確定してからdocumentを実装へ追従させる。

Document rolesは`doc/README.md`を正とする。

更新目安:

- external behavior → `現行仕様書.md`, `機能設計書.md`
- architecture/responsibility → `基本設計書.md`, `ARCHITECTURE.md`
- patch/order/constants → `詳細設計書.md`
- config → `設定ファイル仕様.md`
- power → `電力システム仕様.md`
- future work → `ROADMAP.md`

旧Phase資料は`doc/archive/`へ保存し、現行仕様の根拠に戻さない。

## 11. 完了条件

作業完了は次を満たすことを目標とする。

- code/documentが同じsemanticを説明している
- versionが更新されている
- PR required checkがsuccess
- 実機が必要な項目は確認済み、または未確認と明示
- developへmerge済み
- final develop HEAD/CIを確認
