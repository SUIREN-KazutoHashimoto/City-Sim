# City-Sim 開発・不具合修正手順

この文書は、City-Simで新機能を実装するときと、不具合を修正するときの標準手順を定める。

目的は「とりあえず動く修正」を増やすことではなく、原因・影響範囲・検証方法を残し、後から安全に変更・ロールバック・統合できる状態を維持することである。

現行ソースコードを最終的な正とし、本書とコードが矛盾する場合はコードを確認したうえで本書を更新する。

---

## 1. 基本原則

1. **作業は原則 `develop` の最新から開始する。**
2. **変更前に現行コードを読む。** 名前や過去資料だけで責務を推測しない。
3. **原因と症状を分離する。** 不具合では、見えている症状だけを消す処理を先に入れない。
4. **変更範囲を小さく保つ。** ただし、本来の責務を持つコアを直すべき問題まで無理にpatchへ逃がさない。
5. **1コミットごとに `src/version.ts` の `APP_VERSION` を上げる。** docs-only、型修正、CI修正も例外にしない。
6. **TypeScriptの安全性を全体で弱めない。** `--noCheck`、全体的な `@ts-nocheck`、compiler設定の緩和を修正手段にしない。
7. **CI成功と実機確認を別物として扱う。** build成功だけでは描画・交通・エージェント挙動が正しいとはみなさない。
8. **既存挙動を変える場合は、何を維持し何を変えるかを明示する。**
9. **PRには未確認事項も書く。** 確認していないことを「確認済み」にしない。

---

## 2. ブランチ運用

通常は次の名前を使う。

| 種別 | 例 | 用途 |
|---|---|---|
| feature | `feat/fullscreen-menu` | 新機能 |
| fix | `fix/intersection-deadlock` | 不具合修正 |
| performance | `perf/agent-rendering` | 性能改善 |
| docs | `docs/development-workflow` | 独立した文書整備 |

基本フローは次のとおり。

```text
develop 最新
  ↓
feature / fix / perf / docs branch
  ↓
実装・検証
  ↓
PR → develop
  ↓
CI + 必要な実機確認
  ↓
developへ統合
```

`main` はrelease系統として扱い、通常の開発作業から直接更新しない。`main` へのPRやreleaseは明示的なrelease作業として行う。

既に開いているPRの一部として必要になった文書修正は、そのPRのbranchに含めてよい。ただし、その文書コミットでもversionを上げる。

## 3. 新機能の標準実装手順

### 3.1 要求を実装単位へ分解する

最初に、要求を次の観点へ分解する。

- 外から見える挙動
- データ/状態
- simulation更新
- rendering/UI
- Inspector/一覧/操作
- 設定値
- 永続化の有無
- 性能への影響
- 既存機能との依存関係

UIだけに見える要求でも、対象statusを公開するAPIやruntime snapshotが必要になることがある。逆に、simulation側の変更でも表示だけなら既存storeを参照するだけで済む場合がある。

### 3.2 現行コードの責務を確認する

変更対象のclass/moduleと、その呼び出し元・import元を確認する。

特に以下を確認する。

- 状態の所有者は誰か
- update loopのどこで更新されるか
- 同じ挙動を後段のruntime tuningが上書きしていないか
- `src/version.ts` からimportされるpatch順
- worker/shared memory側にmirrorがあるか
- InspectorやDashboardが別の値を集計していないか

City-Simでは後段patchが最終挙動を決める箇所が多いため、基礎classだけを見て実効挙動を判断しない。

### 3.3 実装方式を決める

次の「Runtime patchを使う基準」を使い、コア変更か独立patchかを選ぶ。

### 3.4 実装する

実装時は、既存の不変条件を壊さないことを優先する。

例:

- Agent/Vehicle/POI IDを途中で詰め直さない
- TypedArrayのcapacityを超えてspawnしない
- reserveしたPOI/parking slotを失敗時にreleaseする
- rendering上の座標とsimulation上の座標を混同しない
- passengerやvehicleのstateを既存システムと互換な形で遷移させる
- patchの再installを防止する

### 3.5 versionを更新する

コミットする変更が揃ったら `src/version.ts` の `APP_VERSION` を1段上げる。

Version更新はコミット単位で行う。後からCI修正コミットを追加した場合は、その修正でもさらにversionを上げる。

### 3.6 buildする

最低限、CIと同じbuild条件を満たす。

```bash
npm ci
npm run build
```

現行CIはNode 24を使用し、`npm run build` 後に `dist/LICENSE`、`dist/NOTICE`、`dist/THIRD_PARTY_NOTICES.txt` の存在とthird-party noticeを検証する。

### 3.7 実機確認する

対象機能に応じてブラウザ上で確認する。

例:

- UI: open/close、入力、保存、再読込、画面サイズ
- 車両: 発進、走行、交差点、到着、再dispatch
- 鉄道: 直線、曲線、駅進入、停車、折返し、夜間
- 人: walk、bus、rail、taxi、目的地到着
- 都市生成: seed違い、中心部/郊外、capacity上限

「起動できた」だけでは完了としない。変更した経路を最低1回通す。

### 3.8 PRを作る

PR本文には最低限、以下を含める。

- 変更目的
- 実装内容
- 変更した重要な数値/条件
- CI結果
- 実機確認結果
- 未確認事項
- 既知の制約

## 4. 不具合修正の標準手順

### 4.1 症状を固定する

修正前に、最低限次を記録する。

```text
症状:
期待する挙動:
実際の挙動:
再現条件:
再現頻度:
影響範囲:
確認したversion / branch:
```

スクリーンショット、動画、seed、時刻、対象ID、交通量など再現に必要な情報があれば残す。

### 4.2 実効コードパスを追う

「怪しそうなファイルを直す」前に、症状が発生するまでの処理を追う。

例: 交通なら

```text
route/path
 → edge/lane selection
 → signal / yield
 → car-following
 → intersection transition
 → rendering interpolation
```

鉄道旅客なら

```text
trip planning
 → station access selection
 → route points
 → passenger state
 → visual Y / XZ sync
 → renderer
```

同じ値が複数moduleで再計算されている場合は、どの値が最終的に描画/状態へ使われているかを確認する。

### 4.3 原因を説明できる状態にする

修正コードを書く前に、少なくとも一文で原因を説明できることを目標にする。

良い例:

> 車線減少時、交差点直進だけmerge許可判定の対象外で、消滅車線の車両が停止線前から永久に進入できなかった。

悪い例:

> たまに止まるので一定時間後に強制移動する。

強制回復処理やguard自体が禁止という意味ではない。壊れた入力・数値異常・回復不能状態からsimulationを守るguardは有効だが、**根本原因が別にある場合はguardだけを最終修正にしない**。

### 4.4 最小の根本修正を入れる

修正対象は、原因を持つ最小責務へ置く。

- lane selectionの誤り → lane/transition側
- state遷移漏れ → state machine側
- 描画位置推定の誤り → actual transformを持つrenderer側
- 集計値の誤り → 集計source側
- 設定不足 → config/default側

別システムに症状を隠す条件を追加するより、原因側の契約を直す。

### 4.5 回帰影響を確認する

修正した条件の反対側も確認する。

例:

- 車線減少を直した → 車線増加/同一車線数/右左折は壊れていないか
- visitor taxi fallbackを強くした → rail/busが利用できる場合までtaxiへ奪われていないか
- platform位置を直した → 直線ホームまで待機範囲が縮みすぎていないか
- workforceを増やした → agent capacity、住宅、visitor headroom、performanceは問題ないか

### 4.6 buildと実機再現確認を行う

不具合修正では、最低でも次の2点を分けて確認する。

1. **元の再現条件で不具合が消えたか**
2. **近接する正常ケースが壊れていないか**

CIだけで再現条件を検証できない不具合は、PRに「実機確認が必要」と明記する。

### 4.7 修正理由を残す

将来コードを見たときに条件の意味が分からなくなる修正には、コメントまたは文書を残す。

ただしコードコメントは「何をしているか」より「なぜその条件が必要か」を優先する。

## 5. Runtime patchを使う基準

City-Simでは `src/version.ts` からruntime tuning moduleをimportし、prototype wrapper等で既存挙動を補正する構成を多く使っている。

Runtime patchが向くケース:

- 既存機能を小さく補正する
- 回帰リスクを局所化したい
- 後から容易に外して比較したい
- UI/Inspector/表示上の追加を既存巨大classから分離したい
- release直後の修正でコア改変を避けたい

コアを直接直す方がよいケース:

- そのclass自身の不変条件が壊れている
- 全呼び出し元で同じ修正が必要
- hot pathでwrapper追加が無駄になる
- patchがpatchを上書きして依存順が複雑化している
- 同一責務に複数世代のpatchが積み重なっている

### 5.1 patch実装ルール

Prototype wrapperは原則次の形にする。

```ts
const proto = Target.prototype as unknown as Record<string, any>;
if (!proto.__citySimExamplePatchVNNN) {
  const previous = proto.method as (...args: any[]) => any;
  proto.method = function patchedMethod(this: Record<string, any>, ...args: any[]): any {
    // before
    const result = previous.apply(this, args);
    // after
    return result;
  };
  proto.__citySimExamplePatchVNNN = true;
}
```

注意点:

- install guardを必ず置く
- `previous` を保存してwrapper chainを維持する
- before/afterの順序を意図的に決める
- return値を失わない
- private memberへ触れるための `Record<string, any>` はpatch境界だけに限定する
- global TypeScript設定を弱めない
- `src/version.ts` のimport順が実行順になることを意識する
- 循環importを増やさない

Patchが増え、どのmoduleが最終挙動を決めるか追えなくなった場合は、次の機能追加より先に統合・整理を検討する。

## 6. `src/version.ts` の扱い

`src/version.ts` は単なるversion定数ではなく、runtime tuningのentry pointでもある。

したがって変更時は2つを確認する。

### 6.1 Version

```ts
export const APP_VERSION = 'x.y.z';
```

コミットごとに必ず上げる。

### 6.2 Import順

後からimportされたpatchが、前のwrapperを包む場合がある。

依存関係があるpatchは順序を明示する。

例:

```text
基礎system
 → behavior tuning
 → integration
 → visual/inspector tuning
```

実装順を変えたときは、同じmethodをwrapしているmoduleがないか確認する。

## 7. 検証レベル

変更内容に応じて、必要な検証を選ぶ。

| Level | 内容 | 代表用途 |
|---|---|---|
| L1 | TypeScript + production build | 全変更 |
| L2 | 起動smoke test | runtime変更 |
| L3 | 対象シナリオ再現 | fix / behavior変更 |
| L4 | 複数seed・長時間simulation | 都市生成・交通・人口 |
| L5 | Performance比較 | rendering / agent / traffic hot path |

L1は必須。L2以降は変更に応じて追加する。

性能改善では「FPSが上がった」だけでなく、simulation throughput、lag、render profile、agent/vehicle countなど同じ条件で比較する。

## 8. CI

現行 `.github/workflows/build.yml` は次を行う。

```text
ubuntu-latest
Node 24
npm ci
npm run build
legal distribution files verification
```

`npm run build` はTypeScript compile、Vite build、legal files copyを含む。

PRのCIが失敗した場合は、ログから最初の実エラーを修正する。CIを通すためだけに型チェックや検証stepを無効化しない。

修正コミットを追加した場合は、そのコミットでもversionを上げる。

---

## 9. PR・統合時のルール

PRは原則 `develop` をbaseにする。

統合前に確認する項目:

- branchが最新の意図したbaseから作られている
- 変更ファイルに想定外がない
- versionがコミット数に応じて更新されている
- CIが成功している
- 必要な実機確認が完了している、または未確認事項が明記されている
- ドキュメント更新が必要な変更では文書も追従している

Merge commitを追加すると「1コミットごとにversion更新」のルールと衝突する場合がある。履歴上fast-forward可能で、branch policy上問題がない場合は、不要なmerge commitを増やさない統合方法を優先する。

## 10. 文書更新の判断

コード変更後は次を目安に文書を更新する。

| 変更 | 更新候補 |
|---|---|
| 外部挙動 | `現行仕様書.md`, `機能設計書.md` |
| システム責務/構造 | `基本設計書.md`, `ARCHITECTURE.md` |
| patch順/定数/不変条件 | `詳細設計書.md` |
| config | `設定ファイル仕様.md` |
| performance計測 | `性能モニタ仕様.md` / 性能設計資料 |
| 開発運用 | 本書 |

Living documentに「現在versionはx.y.z」と固定記載すると、文書更新コミット自身でversionが上がるため自己参照になる。現在versionの正は `src/version.ts` とし、文書には原則として固定versionを埋め込まない。

---

## 11. ロールバック可能性

変更は、問題が起きたときに切り離せることが望ましい。

- 新規patchは1moduleに閉じる
- 関係ないformat変更を混ぜない
- 大規模renameとbehavior変更を同時に行わない
- 設定変更はコード変更と意味を対応付ける
- 一時guardには削除条件をコメントする

独立patch方式を使う主な理由の1つは、問題発生時にimportを外して比較しやすくすることにある。

---

## 12. 完了条件

新機能または不具合修正は、以下が揃って完了とする。

```text
[ ] 要求/症状を説明できる
[ ] 実効コードパスを確認した
[ ] 実装方式を選んだ理由がある
[ ] APP_VERSIONを更新した
[ ] npm run buildが成功した
[ ] CIが成功した
[ ] 必要な実機確認を行った
[ ] 回帰確認を行った
[ ] 必要な文書を更新した
[ ] PRに未確認事項を含めて記録した
```

CIで確認できない視覚・simulation挙動が残る場合は、それを隠さず完了条件から切り分け、「コード実装・build完了 / 実機確認待ち」と明示する。
