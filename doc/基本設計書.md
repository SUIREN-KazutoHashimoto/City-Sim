## 2. システム概要

City-Sim は TypeScript / three.js / Vite で構成するブラウザ向けリアルタイム都市シミュレーションである。

都市を静的に表示するだけではなく、市民、建物、POI、道路、歩道、自家用車、路線バス、鉄道、物流、信号、施設在庫を時間経過に沿って相互作用させる。

現行の主要機能:

- 100km²級の手続き型都市生成
- CBD、副都心、住宅、商業、産業、物流、公共施設、公園を含む都市計画
- 道路階層とBlock/Parcel生成
- 5万人級のAgentシミュレーション
- Utility AIによる生活行動
- 徒歩、自家用車、バス、鉄道による移動
- 道路/歩道のA*経路探索
- IDM系車両追従、車両信号、歩行者信号
- 店舗在庫と物流配送
- 道路回廊型の高架鉄道生成
- 普通/快速/特急、閉塞、信号、ダイヤ、渡線、車両基地
- Agentの実列車への乗降、駅構内3D移動、最大1回乗換
- GPU Instancingを中心とした3D描画
- LOD / Worker / SharedArrayBufferを用いた大規模化対応
- Inspector、24時間活動グラフ、Performance Monitor

## 4. 設計方針

### 4.1 データ指向 + 薄いOOP

大量の市民・車両はSoA（Structure of Arrays）で保持する。

```text
AgentStore
  posX[] / posZ[]
  state[]
  needs[]
  homePOI[] / workPOI[]
  car[]
  bus data[]
  ...

VehicleStore
  posX[] / posZ[]
  speed[]
  road edge[]
  driver[]
  vehicle type[]
  ...
```

ドメイン上の外部API、Renderer、Inspector等では必要に応じてクラス/ファサードを使用する。

### 4.2 System / Store / Coordinator分離

- **Store**: 大量状態を保持する。
- **System**: Storeを走査して状態更新する。
- **World**: Agentの意思決定、移動手段切替、POI予約等を統合する。
- **RailRenderer**: 現状は鉄道運行状態も保持する独立サブシステム。旅客側へTransit Provider APIを公開する。
- **Rendering**: three.js Meshへ状態を同期する。

### 4.3 描画とシミュレーションの分離

`requestAnimationFrame` の描画周期とシミュレーション時間を分離する。`SimulationClock` がtimeScaleとstepを管理し、高倍率時も最大substep数を制限する。

### 4.4 大規模実行

Cross-Origin Isolation環境ではSharedArrayBufferを使用する。Agent/Pedestrian/POI検索等をWorkerへ分散し、main threadは状態遷移や予約確定を担当する。

### 4.5 GPU Instancing

建物、歩行者、車両、線路設備、駅部材等はプリミティブ + InstancedMeshを基本とする。高ポリゴン個別モデルを大量に生成しない。

- RailRenderer
- 鉄道拡張描画
- Inspector
- Dashboard
- Performance Monitor

## 7. 都市モデル

### 7.1 都市計画

主なDistrict:

- CBD
- Commercial
- MixedUse
- ResidentialHigh
- ResidentialLow
- Industrial
- Logistics
- Civic
- Park

都市化度だけではなく、密度、地価、中心影響、用途適性を分離する。

### 7.2 道路

道路階層:

```text
Highway > Arterial > Collector > Local > Path
```

RoadNetworkは有向Edgeを基本とし、双方向道路は方向別Edgeを持つ。

### 7.3 Block / Parcel

街区をParcelへ分け、間口/奥行/setback/駐車/統合/開発強度を保持する。建物用途と建築アーキタイプは別概念とする。

## 8. Agentモデル

主要属性:

- 位置、速度、向き
- energy / hunger / social / hygiene / fun
- wealth / age / extrovert
- occupation / workStart / workEnd
- homePOI / workPOI / goalPOI
- state
- 徒歩経路
- 自家用車情報
- バス乗降情報

鉄道固有のboard/alight/train情報は現状 `RailPassengerIntegration` のsidecar TypedArrayに保持し、AgentStore本体へ全項目を追加しない。

現行状態:

```text
Idle / Routing / Traveling / Engaged
ToVehicle / Driving
ToBusStop / WaitingBus / OnBus
ToRailStation / WaitingTrain / OnTrain
```

## 9. 交通モデル

### 9.1 徒歩

SidewalkNetwork上で経路探索し、歩行者信号・横断歩道・車両占有を考慮する。大規模実行ではPedestrian WorkerがSharedArrayBuffer上のAgent座標を更新する。

### 9.2 自家用車

駐車スロットを確保し、RoadNetwork上をTrafficSystemで走行する。追従はIDM系モデルを使用する。

### 9.3 バス

一般道路交通と同じTrafficSystemを利用し、停留所でAgentが乗降する。

### 9.4 鉄道

鉄道は道路交通とは別の運行系を持つ。

- RailNetworkPlan: 路線/駅/線形計画
- RailRenderer: 列車、閉塞、信号、ダイヤ、運行
- RailPassengerIntegration: Agentと列車を接続

旅客は実際にホームまで3D移動し、停車中の実列車へ乗る。

---

## 10. 鉄道基本設計

### 10.1 線形

道路回廊を利用するが、道路Nodeを細かく追従しない。回廊内で折れ点を簡略化し、長い直線と必要なカーブを生成する。

### 10.2 複線

幹線は右側通行。1駅間を方向別3閉塞へ分割する。

### 10.3 信号

信号は直後閉塞を制御し、その次の閉塞を予告に使う。

- red: 直後不可
- yellow: 直後可、次不可
- green: 2閉塞先まで可

ホーム内部は物理信号を省略して仮想閉塞として運用する。

### 10.4 ダイヤ/種別

普通、快速、特急を持ち、05:00–23:30を基本営業時間とする。朝夕ピークでは予備普通を運用する。

### 10.5 終端/基地

終端駅は4線ファン。車両基地は実終端駅に限定し、8線×約260mの短く横広い構成とする。

---

## 11. 鉄道旅客設計

### 11.1 Transit Provider

WorldはRailRendererへ直接内部依存せず、旅客用Provider APIを介して次を取得する。

- 乗車可能な停車中列車
- 列車位置
- 駅/ホームアクセス座標

### 11.2 経路

鉄道経路は直通または1回乗換。徒歩アクセス、待ち時間、列車時間、乗換時間を概算し、徒歩より十分有利な場合に鉄道を選択する。

### 11.3 駅内移動

駅入口、地上階段、ホーム間階段、ホーム待機位置を3D座標で移動する。ホーム到着前には乗車不可。

複数階駅は上層→下層→最下層→地上という階層接続を基本とする。

---

## 12. 描画設計

### 12.1 Renderer互換

`InstancedRenderer` の代表MeshをInspector/Raycast互換として維持し、`EnhancedRenderer` やOverlayが可視部材を追加する。

### 12.2 鉄道

RailRenderer上に次を追加する。

- 列車外装/窓/路線帯/種別帯
- 線路・駅照明
- 前照灯/尾灯
- 発車案内灯/接近案内灯
- 道路回避型の高架支持
- 空洞を保持した駅外装
- 駅階段/通路

### 12.3 駅外装

駅内部をSolid Boxで埋めず、薄い壁、ガラス、フレーム、屋根を外周へ配置する。中央/端部に開口を残す。

## 14. 性能方針

- SoA TypedArray
- SharedArrayBuffer
- Worker Pool
- GPU Instancing
- Static geometryの一括構築
- LOD
- Spatial index
- POI検索の事前索引/Worker化

## 15. 鉄道Patch構成上の注意

現状の鉄道機能は `RailRenderer` コアに加えてPrototype Patch型モジュールを段階適用している。後段のPatchが前段実装をラップするため、import順が仕様の一部になっている。

安定後はコアへ統合して依存関係を明示化することが望ましいが、現時点では `現行仕様書.md` と `詳細設計書.md` に記載した順序を維持する。

---

## 16. 既知の設計上の制約

- 鉄道旅客は最大1回乗換。
- 鉄道定員は1両120人の簡易容量。
- 駅内旅客流動、扉位置、乗降時間は簡略モデル。
- 基地入出庫は本線運転より簡略化。
- 完全なSeed決定論は未保証。
- Prototype Patchのimport順依存がある。
