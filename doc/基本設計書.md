## 1. 文書情報

## 2. システム概要

City-Sim は、ブラウザ上で動作するリアルタイム都市シミュレーションである。

都市そのものを描画するだけでなく、市民・自家用車・路線バス・配送トラック・道路・歩道・信号・建物・POI・店舗在庫を相互作用させ、都市活動を時間経過に沿って発生させる。

現行実装の主な特徴は以下のとおり。

- ノイズベースの手続き型都市生成
- 市民ごとの職業・勤務時間・欲求・資産・性格・自宅・職場の保持
- Utility AI による行動選択
- 徒歩、自家用車、路線バスによる移動
- 道路グラフ・歩道グラフを分離した経路探索
- A* による経路探索
- IDM 相当の車両追従
- 通常信号・スクランブル信号
- 駐車場および駐車スロット管理
- 店舗在庫と配送トラックによる補充
- three.js InstancedMesh を使用した大量描画
- 市民・車両・建物のインスペクト、追跡
- シミュレーション速度変更と24時間活動グラフ
- 建物用途と建築アーキタイプを分離した建物多様化
- プリミティブ複合形状による建物・車両・歩行者・街路設備の強化描画
- シミュレーション時刻に連動した昼夜ライティング

## 5. アーキテクチャ方針

### 5.1 OOP とデータ指向設計の併用

大量エージェントを処理するため、各市民・車両を重い独立オブジェクトとして毎フレーム更新する方式は採用しない。

実データは SoA（Structure of Arrays）形式の Store に保持する。

```text
AgentStore
  posX[]
  posZ[]
  energy[]
  hunger[]
  state[]
  ...

VehicleStore
  posX[]
  posZ[]
  speed[]
  edge[]
  state[]
  ...
```

その上で、外部APIやドメイン表現が必要な箇所では `GameObject` / `Pedestrian` のような薄いOOPファサードを使用する。

### 5.2 System / Store 分離

- Store: 状態を保持する。
- System: Store を走査して状態遷移を行う。
- World: System 間の配線、実行順序、複合状態遷移を管理する。
- Rendering: シミュレーション状態を描画へ同期する。

### 5.3 シミュレーションと描画の分離

シミュレーションは `SimulationClock` のステップで更新し、描画は `requestAnimationFrame` で行う。

描画FPSが変動しても、シミュレーションロジックの時間進行を分離できる構造とする。

### 5.4 描画互換レイヤ

既存の `InstancedRenderer` をInspector互換の基底Rendererとして維持し、`EnhancedRenderer` が可視ディテールを追加する。

代表Meshのinstance indexとStore index対応を崩さず、追加可視MeshをRaycast対象へ直接混在させない。

## 8. レイヤ・責務

### 8.1 core

汎用基盤。

- シミュレーション時間
- 空間ハッシュ
- 距離、補間、乱数等の数学関数

ドメイン依存を持たせない。

### 8.2 generation

都市静的データの生成。

- 都市化度
- 道路
- 建物
- 建物アーキタイプ / 外観Seed
- POI
- 駐車場
- 外部ゲート

同一seedで概ね同一都市を再現できることを意図する。

### 8.3 agents

市民の状態と意思決定。

- 市民SoAデータ
- 欲求減衰
- Utility AI
- OOPファサード

### 8.4 traffic

移動ネットワークと車両交通。

- 道路
- 歩道
- A*
- 自動車
- 信号
- バス
- 物流

### 8.5 world

ドメイン統合。

`World` は複数システムを組み合わせて「市民が目的地を決め、移動し、施設で活動する」一連の状態遷移を管理する。

### 8.6 rendering

three.js とUI。

シミュレーションロジックを直接所有せず、Store / World から読み取った状態を表示する。

`EnhancedRenderer` は `InstancedRenderer` を継承し、基本GeometryのInstancingを維持したまま、建物・車両・歩行者・道路・街路設備の複合形状を構成する。

## 9. 主要データモデル

### 9.1 Agent

主な属性:

- 位置、速度、向き
- energy / hunger / social / hygiene / fun
- wealth / age / extrovert
- occupation / workStart / workEnd
- homePOI / workPOI / goalPOI
- state
- 徒歩経路
- 車所有情報
- バス乗降情報

### 9.2 Vehicle

自家用車、バス、トラックを同一Storeで管理する。

主な属性:

- 位置、向き
- speed / maxSpeed / accel
- IDMパラメータ
- 道路Edge上の進捗
- 経路
- driver
- 駐車場、駐車スロット
- isBus / busId
- isTruck / truckId

### 9.3 POI

市民行動の目的地。

カテゴリ:

- Home
- Work
- Food
- Retail
- Leisure
- Health
- Education
- Parking

`Health` と `Education` は型として定義済みだが、現行の主要な都市生成・Utility AI では未活用。

主な属性:

- category
- 座標
- priceTier
- capacity / occupancy
- buildingId
- stock / maxStock

### 9.4 Building

従来の位置・寸法・階数・主用途に加え、描画用の建築情報を保持する。

- archetype
- roofType
- palette
- styleSeed
- rotation
- urbanity

`POICategory` は用途、`BuildingArchetype` は建築形状を表し、1対1にはしない。

### 9.5 RoadNetwork

道路は有向グラフとして保持する。

RoadNode:

- id
- x / z
- edges
- hasSignal

RoadEdge:

- from / to
- length
- lanes
- speedLimit
- roadClass
- occupants

### 9.6 SidewalkNetwork

道路とは別グラフ。

- Highway には歩道を生成しない。
- 道路両側に歩道を生成する。
- 交差点部分には crossing Edge を生成する。

## 11. World.step 実行順

現行の実行順は以下。

1. `SignalSystem.update`
2. `NeedSystem.update`
3. Idle市民のUtility AI評価
4. Routing市民の移動開始処理
5. 歩行者/車両の交差点占有状態計算
6. `TrafficSystem.update`
7. `BusSystem.update`
8. バス乗客座標同期
9. `LogisticsSystem.update`
10. 移動中歩行者の空間インデックス再構築
11. 徒歩移動
12. 到着自家用車処理
13. 施設滞在処理

新規Systemを追加する場合は、この順序依存を明示すること。

## 12. 時間設計

`SimulationClock` の基本固定ステップは 1/30 秒。

- `timeScale` により現実秒あたりのシミュレーション時間を変更する。
- 最大サブステップは40。
- 大きな時間蓄積時には、蓄積時間を最大40ステップへ分配する。

現行速度プリセット:

- 0.5×
- 1×
- 5×
- 30秒/秒
- 1分/秒
- 3分/秒
- 10分/秒
- 30分/秒
- 1時間/秒

## 13. 経路探索設計

共通 `PathGraph` インターフェース上で A* を使用する。

### 車両

コスト = `edge.length / edge.speedLimit`

概算所要時間が短い経路を優先する。

### 歩行者

コスト = `edge.length`

距離最短を優先する。

Open Set はバイナリヒープで管理する。

## 14. 交通設計

### 14.1 車両追従

各道路Edgeの `occupants` を `segT` 順にソートし、直前車との距離を取得する。

IDM相当の式で加速度を計算し、以下を自然発生させる。

- 加速
- 車間維持
- 減速
- 停止
- 車列
- 渋滞

### 14.2 信号

- Concurrent: 車両方向と対応歩行者方向が進行
- Scramble: 車両全赤の歩行者一斉横断フェーズを追加

### 14.3 歩車相互作用

- 歩行者は赤信号または交差点付近の車両を検出すると待機する。
- 車両は赤信号または横断歩行者を検出すると停止線へ向けて減速する。

## 15. 移動手段設計

基本判定:

- 180m以上を遠距離とする。
- 90m以上かつ energy < 0.4 も遠距離とする。

優先順:

1. 利用可能な自家用車
2. 同一路線で結べるバス
3. 徒歩

自家用車では目的地近傍駐車場を先に予約し、徒歩→車→徒歩の複合移動を行う。

バスでは現在地・目的地双方から350m以内の停留所を探索し、共通路線が存在する場合のみ利用する。

---

## 16. 施設利用・在庫設計

市民は目的POIを移動開始時に `reserve()` する。

`occupancy` は「施設内人数」だけでなく「利用枠予約済み人数」を含む意味となる。

Food / Retail は在庫を持ち、利用完了時に1減少する。

在庫0のPOIは目的地として利用不可。

物流トラックは在庫率60%未満の店舗を配送候補とし、外部ゲートから補充する。

## 17. 描画設計

大量オブジェクト描画には `THREE.InstancedMesh` を使用する。

### 17.1 静的描画

- 地面
- 道路
- センターライン
- 歩道
- 駐車場
- 建物
- 信号設備
- 横断歩道
- 停止線
- バス停
- 外部ゲート
- 縁石
- 中央分離帯
- ガードレール
- 駐車区画線
- 街灯
- 樹木

### 17.2 動的描画

- 市民
- 自家用車
- バス
- トラック
- 信号灯色

Storeを正とし、描画Instanceへ毎フレーム同期する。

### 17.3 建物強化描画

建物用途と建築アーキタイプを分離する。

現行アーキタイプ:

- DetachedHouse
- TownHouse
- LowRiseApartment
- MidRiseApartment
- ResidentialTower
- SmallOffice
- OfficeSlab
- OfficeTower
- SmallShop
- RetailBox
- CommercialBlock
- MixedUse
- LeisureHall

可視建物はShell / Upper volume / Facade panel / Roof / Rooftop equipment / AwningのInstanced primitive部品で構成する。

元の建物Boxは透明なRaycast hit proxyとして残す。

### 17.4 歩行者強化描画

元Capsuleは透明なRaycast hit proxyとし、Torso / Head / 左右Legを可視化する。歩行中はシミュレーション時刻に応じて左右脚を逆位相で振る。

### 17.5 車両強化描画

既存BodyにCabin / Wheel部品 / Front lamp / Rear lampを追加する。自家用車はIDから複数の比率差を生成し、Bus/Truckは専用寸法を用いる。

### 17.6 昼夜環境

`SimulationClock.dayPhase` から太陽位置を算出し、背景/Fog/DirectionalLight/HemisphereLightを更新する。

## 20. 現行制約

- バス乗換は未実装。共通1路線のみ。
- バス時刻表・運行間隔最適化は未実装。
- 車線変更は未実装。
- 右左折専用レーン、信号矢印は未実装。
- 渋滞を考慮した再経路探索は未実装。
- 歩行者回避は簡易分離ベクトル。
- 建物内部移動は未実装。
- `Health` / `Education` は主要機能未接続。
- 本格的な経済、企業、税、家賃、生産は未実装。
- 現状は約10km²規模であり、150km²級ではLODが必要。
- 窓は個別GeometryではなくFacade panelによる抽象表現。
- 車両外観差は描画専用で、走行性能差には接続していない。
- 街灯発光は現状固定で、夜間のみ点灯する制御は未実装。
