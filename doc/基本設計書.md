# Machi-Sim 基本設計書

> Target: `develop` / synchronized at v1.0.30 / 2026-08-27. **現行ソースコードを正とする。**

## 1. 目的

本書はMachi-Simの設計原則、責務境界、データ所有と重要な不変条件を定義する。現行の具体的数値は`現行仕様書.md`/`設定ファイル仕様.md`、機能単位の仕様は`機能設計書.md`、patch順と実装定数は`詳細設計書.md`を参照する。

## 2. システム概要

Machi-SimはTypeScript / three.js / Viteで構成するブラウザ向けリアルタイム都市シミュレーションである。同一simulation time上で以下を相互作用させる。

- 都市計画、道路、Block/Parcel、Building/POI
- 公園、森林、農場、産業、fleet depot
- 市民、勤務、食事、買物、娯楽
- 徒歩、自家用車、バス、タクシー、Truck
- 在来鉄道、外部高速鉄道、実旅客
- 発電、地下電力網、変電所、需要家、電力品質、燃料物流
- 描画、Inspector、F10全画面メニュー、Performance

## 3. 設計原則

### 3.1 コード優先

設計書は実装の上位契約ではない。コードと文書が食い違う場合、最終import後の実効動作を確認して文書を更新する。

Prototype Patchを使う分野ではbase classだけで仕様を確定しない。

### 3.2 データ指向

大量Agent/VehicleはSoA TypedArrayで保持する。Cross-Origin Isolationが使える場合はSharedArrayBufferを利用し、Workerへ大規模stateを複製しない。

### 3.3 Coordinator / Store / System / Renderer

- Store: 大量状態を保持
- System: Storeやnetworkを走査し局所ルールを更新
- World: 行動、POI、移動手段、複数System間の遷移を統合
- Renderer: simulation stateをthree.jsへ同期
- UI/Inspector: snapshot/APIを読んで診断・操作を提供

RailRendererは現状operation/render責務を一部併有する。

### 3.4 Simulationと表示を分離

render-time補間や見た目の補正はsimulation判定を置換しない。道路右左折、Building detail、power facility marker等も、可能な限りlogical stateを変えず表示層へ閉じ込める。

### 3.5 実体の一意性

同じ施設をsimulation用とrender用に別座標で二重生成しない。

電力施設はこの原則に従い、通常CityGenerator Buildingを施設へ用途転換し、そのBuildingをPowerSystem、Work POI、物流、Inspector、Raycast、LOD、jumpの共通実体とする。

### 3.6 Runtime tuning chain

`src/version.ts` は版番号とruntime tuning import入口を兼ねる。同じmethodを複数moduleがwrapするためimport順を仕様の一部として扱う。

Patchが恒久設計になった場合は、無制限にwrapperを積まずコア統合を検討する。

## 5. ソース領域の責務

### `src/core`

### `src/config`

### `src/generation`

都市計画、道路、Block/Parcel、Building/POI、特殊施設、公園、農場/郊外産業、fleet depot、電力施設Building予約、最終land-use refinement。

### `src/traffic`

## 6. 都市生成設計

Base generation:

```text
Planning → Road → Block/Parcel → Building/POI → Facilities/Parks
```

後段refinementは、生成時点で確定できない横断条件を適用する。

- urban footprint / diversity
- rural industry / farms
- station clearance
- park trim
- power-facility Building reservation

既に他用途へ予約されたBuildingを別施設が奪わないよう、production/facility/depot/infrastructure metadataを予約集合として扱う。

## 7. 産業・職場設計

### 7.1 物理生産

```text
設備/面積 → base production
attendance × power → operating efficiency
base × efficiency → actual output
```

Farmはfield areaをbase productionへ使う。Money economyとは分離する。

### 7.2 一般職場

- assigned: 在籍
- present: 物理的に現在出勤中
- capacity: 定員

一般のphysical productionではpresentをattendanceとして扱う。

### 7.3 ライフライン職場

ライフラインは「今建物内にいるか」と「そのシフトへ出勤済みか」を分ける。

- scheduled: 現在シフト対象
- present: 現在POI内
- onDuty: 現シフトでcheck-in済み、またはhandover/startup grace中
- concurrentStaff: 100%運転に必要な同時勤務目標

短い食事/休憩を理由に巨大設備が瞬間的に大幅出力低下しないよう、発電能力はonDuty基準とする。一方、一度もcheck-inしない欠勤はgrace終了後に能力低下へ反映する。

## 8. 電力設計

### 8.1 BuildingとPower Asset

Power assetの論理IDと地上施設Buildingはbindingで対応付ける。地上施設の位置・道路アクセス・勤務POI・UI jumpはBuildingを正とする。

### 8.2 地下系統

道路Edgeを地下line topologyに再利用する。通常表示では電線・電柱を描画しない。

### 8.3 hard / soft constraints

現在の配電では、接続障害・設備offline/fault・Zone供給源容量をhard constraintとする。健全なline/substation定格はoverload diagnosticとして扱う。

即時rating clippingで需要を落とすのではなく、供給後にoverloadを計測する。将来のthermal accumulation / trip / recoveryへ接続可能な設計とする。

### 8.4 発電と物流

発電所available outputはstaffing/fuelに依存する。火力燃料は実Truck物流でのみ受け入れる。これにより人員、交通、産業在庫、電力供給を同一simulationへ接続する。

## 9. 道路・公共交通設計

TrafficSystemの論理path/edge/segTを正とし、lane runtimeとturn displayはsidecar/wrapperで拡張する。

Pedestrianはsignal待ちでrouteを捨てない。

Busは短距離local networkを形成し、Taxi/Bus/Freightは専用depotから運用する。

## 10. 鉄道設計

Planning station、physical station/access、roadNode、running lineを区別する。駅建築と旅客動線はfinal smoothed railと矛盾しないようにする。

列車編成位置は単一running distanceを基準とし、車両単位描画はそこからsampleする。

## 11. 描画・UI設計

反復geometryはInstancedMeshを基本とし、Building/Agent/Vehicleは距離LODを持つ。

UIはsimulation stateをコピーして独自の真実を作らず、snapshot/registry/bindingを参照する。

F10全画面メニューは一覧の上にanalysis layerを持つ。Chartは現在SVG/CSSの軽量実装で、外部chart dependencyを増やさない。

Jumpは「表示文字列から概算座標へ飛ぶ」のではなく、対象entity/Buildingを解決してからカメラ移動する。

## 12. Performance設計

- SharedArrayBuffer / Worker
- SoA
- active/dirty list
- spatial index
- A* cache
- GPU instancing / LOD
- separate simulation/render/rail budget
- power topology/path/consumer cache

性能最適化は挙動を変えないことを原則とし、変更が必要な場合は仕様変更として扱う。

## 13. 重要な不変条件

1. ソースコードと最終runtime overrideを仕様の正とする。
2. `src/version.ts` import順変更時はpatch chainを再監査する。
3. Rendering補正でlogical Road/Power stateを不必要に書き換えない。
4. Pedestrian signal待ちでwalk routeを破棄しない。
5. Farm logistics sourceとfield extentを分離する。
6. Power facilityは実Buildingと論理assetのbindingを一意に保つ。
7. 発電staffingはlifeline onDuty semanticsを使い、瞬間presentへ戻さない。
8. 健全なline/substation ratingを即時load-shedding hard capへ戻す場合は、保護/trip仕様を同時に設計する。
9. Station platform/accessはrunning railから独立した矛盾軌跡へ置かない。
10. Render filter / analytics / overlayはsimulation stateを勝手に変更しない。

## 14. 技術的負債

- RailRendererのoperation/render責務混在
- Prototype Patchの順序依存
- `version.ts` のversion/import二重責務
