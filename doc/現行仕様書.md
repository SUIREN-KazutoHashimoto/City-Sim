## 2. 標準起動設定

`public/config/city.json` の生設定:

| 項目 | 値 |
|---|---:|
| Seed | `random` |
| 都市面積 | 100 km² |
| 都市一辺 | 10 km |
| 市街地目標比率 | 0.40 |
| 基準街区 | 90 m |
| 初期人口 | 50,000 |
| Agent capacity | 60,000 |
| Vehicle capacity | 30,000 |
| 副都心数 | 3 |
| Arterial間隔 | 900 m |
| Collector間隔 | 360 m |
| Industrial比率 | 0.08 |
| Park計画比率 | 0.055 |
| 鉄道 | 有効 |
| 幹線鉄道路線 | 3 |
| `railStationSpacing` 基準値 | 525 m |
| 駅影響半径 | 900 m |
| 副都心支線 | 有効 |

### 2.1 駅間隔の実効仕様

`railStationSpacing=525` は全駅の固定間隔ではなく、駅配置の基準値。

`RailRuralStationSpacing` はCBD付近を係数1.0、都市外縁を係数2.0とする滑らかな locality factor を使う。したがって通常設定では、おおむね:

```text
中心部: 約525 m基準
    ↓
郊外: 徐々に拡大
    ↓
外縁: 最大約1,050 m基準
```

になる。

### 2.2 `parkRatio` の意味

`planning.parkRatio=0.055` は初期都市計画の入力値。最終公園数は後段生成で再整理されるため、最終的に市域の5.5%が公園になるという意味ではない。

---

## 3. 起動・シミュレーション時間

1. `CityConfigLoader` が設定を読込・検証し、Seedを解決する。
2. `World` が都市を生成する。
3. `src/version.ts` から読み込まれるruntime tuning群が生成・交通・物流・描画等を拡張する。
4. Loading中に通常simulationを事前進行し、表示開始直後の大量Idle/route burstを消化する。
5. 静的描画、鉄道、動的Mesh、UIを構築する。
6. `requestAnimationFrame` とsimulation stepを分離して進行する。

高倍率時はWorld処理をbatch化し、lag/backlogに応じて描画頻度を調整する。Railは独立したframe budget/backlogを持つ。

# 都市生成

## 4. 都市計画・道路・街区

### 4.1 District

主なDistrict:

- CBD
- Commercial
- MixedUse
- ResidentialHigh
- ResidentialLow
- Industrial
- Logistics
- Civic
- Park

`urbanScore`、`landValue`、`density`、`centerInfluence`、`transitInfluence` は別値として扱う。

### 4.2 道路階層

```text
Highway > Arterial > Collector > Local > Path
```

標準生成の車線数は1方向あたりの本数として扱う。

- Arterial:
  - CBD / Commercial: 3車線
  - その他: 2車線
- Collector:
  - density > 0.72: 2車線
  - その他: 1車線
- Local: 通常1車線

Local道路は密度/地区に応じて一部省略される。低密度・郊外ほど道路密度を下げる。

### 4.3 Block / Parcel / 建物

道路で囲まれた街区をBlockとして抽出し、Parcelへ分割する。frontage、parcel depth、setback、parcel統合、development intensity、coverage ratio、FAR等から建物を生成する。

建物高さ帯は:

- super-high-rise
- high-rise
- mid-rise
- low-rise

としてruntime metadataを持つ。

---

## 5. 公園・森林・道路上樹木

### 5.1 公園

生成途中ではPark districtや特殊施設計画により公園候補が作られるが、最終段で高さ帯に応じて公園を削減する。

目安上限:

| 周辺高さ帯 | 公園数 / 対象Block |
|---|---:|
| 高層・超高層 | 約2% |
| 中層 | 約1% |
| 低層 | 約5% |

この処理は**余剰公園を削るだけ**で、不足分を追加生成しない。したがって実際の比率は上記を下回る場合がある。

### 5.2 森林

市街地外や空き地に森林spaceを生成する。農地へ転用された領域と重なる森林は除去される。

### 5.3 車道上の木

`TreeRoadClearanceTuning` は道路Edgeの実幅を使って最終描画時に樹木位置を検査する。

道路中心線から:

```text
roadWidth(lanes) / 2 + 約1.8 m
```

以内の街路樹/森林樹木は描画しない。

---

## 6. 駅周辺土地利用

駅周辺は次の2種類のclearanceで保護する。

### 6.1 実線路包絡clearance

`RailStationClearance` が線路・駅設備へ直接干渉する建物/駐車場を除去する。

### 6.2 最終駅前建築禁止clearance

`CityGenerationRefinement` が全建物を生成後に再検査する。

基本半径:

- Central / SubCenter: 78 m
- Local / Terminal: 56 m

判定は:

```text
駅中心から建物中心までの距離
<
基本半径 + 建物footprint半対角
```

なら抵触とみなす。

抵触建物はPOIも無効化する。特殊施設、農場、工場等が抵触した場合は関連するfacility/runtime production registryからも除去する。

この最終clearanceにより、「駅付近に一般建物を建てない」仕様を後付け施設も含めて維持する。

# 郊外産業・農地・職場

## 7. 営業所

都市生成後、道路アクセス可能な場所へ次を各1拠点生成する。

- タクシー営業所
- バス営業所
- 物流営業所

各営業所は専用駐車区画を持ち、一般住民用Parking POIとしては利用しない。

バス、タクシー、産業トラックは対応営業所を運用拠点として使う。

---

## 8. 農地

### 8.1 構成

現行農場は単体warehouseではなく、複数街区規模のland-use estateとして扱う。

1農場:

```text
大型の畑
+ 農場事務所
+ 農場倉庫
```

を持つ。

初期農地区画候補は複数Block形状から選択し、後段で道路・他建物・他農場と衝突しない場合はさらに畑を拡張する。

### 8.2 道路

農地区画を計画した後、その内部を横切る一般道路を生成しない。境界側の主要道路をアクセスに使う。

### 8.3 物流位置と描画位置

- `site.x/z`: 倉庫側。トラック積込の物流source
- `fieldX/Z`, `fieldWidth/Depth`: 畑全体。描画と面積計算

を分離する。

### 8.4 生産能力

農場の100%稼働時の基礎 `processRate` は畑面積で決定する。

現行式:

```text
fieldArea = fieldWidth × fieldDepth
baseProcessRate = max(6, fieldArea / 7000)
```

在庫容量も畑面積に比例する。

したがって同じ稼働率でも、広い農場ほど絶対生産量が多い。

---

## 9. 産業サプライチェーン

Production kind:

- `farm`
- `raw-factory`
- `processor`
- `assembler`

物流段階:

```text
farm / raw-factory
      ↓ stage 0
processor
      ↓ stage 1
assembler
      ↓ stage 2
Retail / Food
または
city gate export
```

processor/assemblerは入力在庫を消費して0.92倍のoutputへ変換する。

産業物流truckは物流営業所をhomeとし、明示的に:

```text
idle
→ sourceへ移動
→ loading
→ destinationへ移動
→ unloading
→ depot return
```

を行う。

truck cargo capacityは240。fleet sizeはproduction site数から計算し、18～72台へclampする。

---

## 10. 職場人数・生産効率

### 10.1 人数の意味

- **出勤**: そのWork POIへ割り当てられ、現在 `Engaged` かつgoal/work POIが一致しているAgent
- **在籍**: `workPOI` がその職場を指す全Agent
- **定員**: Work POI capacity

農場は事務所と倉庫のWork POIを合算する。

### 10.2 効率

生産拠点:

```text
efficiency = clamp(出勤 / 定員, 0, 1)
actualProcessRate = baseProcessRate × efficiency
```

農場/原料工場/加工工場/組立工場では、この効率が物理生産量へ直接反映される。

一般office/commercial等では同じ出勤状況を「稼働効率」として表示するが、現時点で金銭・売上・価格等の経済モデルへは接続していない。

### 10.3 Inspector

職場系表示例:

```text
職場種別 加工工場
出勤 18 / 在籍 31 / 定員 40 / 生産効率 45%
```

職場種別には農場、原料工場、加工工場、組立工場、office、商業、飲食、hotel、warehouse/logistics、各fleet depot等を表示できる。

# 市民・道路交通

## 11. 市民・移動手段

Utility AIが勤務、食事、買物、娯楽、帰宅等を評価し、POI容量/在庫を考慮して目的地を選ぶ。

主な移動手段:

- 徒歩
- 自家用車
- 路線バス
- タクシー
- 在来鉄道

タクシー固有状態はside dataとして保持し、base AgentState互換のためwaiting/onboard時には既存bus系stateを再利用する。

---

## 12. 道路車両・多車線交通

自動車、truck、bus、taxiはRoadNetwork A* routeを使用する。

TrafficSystemが:

- Edge進行
- signal
- pedestrian block
- occupancy
- IDM系追従
- 到着

を処理する。

`MultiLaneTrafficTuning` がlane runtimeを追加し、右左折方向や道路車線数に応じたtarget laneを選択する。

### 12.1 車線減少と右左折

右左折レーン要求と、次道路の少車線化要求が競合しないよう `TurningLaneTransitionFix` が交差点turn時だけ次Edgeのlane count参照をvirtualizeする。

実道路metadataは変更しない。Edge切替時には実lane countへclampする。

### 12.2 右左折の見た目

多車線化後、Edge切替時にlane offsetだけが瞬時に変わると車体が横滑りして見える。

`TurningVisualPathTuning` は交差点内表示だけ、進入側の実turn lane中心から退出側lane中心へquadratic curveで補間する。

補間距離:

- passenger car: 15 m
- truck: 21 m
- bus: 25 m

論理的な道路占有/route判定はEdgeベースのまま。

---

## 13. 横断歩道

`PedestrianCrossingSafetyTuning` が歩行者の横断中occupancyを維持し、進入車両へblockを出す。

赤信号時の歩行者は経路を捨てない。

`PedestrianSignalWaitTuning` により:

1. 赤信号でも横断歩道入口へ接近
2. entryから約1.15 m手前で停止
3. route/pathCursorを保持
4. 歩行者信号が青、かつ車両競合なしになるまで待つ
5. 同じ横断歩道を渡る

という挙動になる。

---

# バス・タクシー

## 14. バス

### 14.1 路線構成

base BusSystemは3本×2軸の6本grid line候補と停留所を作る。

`ShortBusRouteTuning` はその長距離lineを短距離routeへ再構成する。

- 各元lineを最低4分割
- Road A*による実走行距離を測定
- 1routeの循環総延長を5,000 m以下に制限
- 目標は約4,600 m
- 分割境界のstopは複数routeで共有可能

標準10 km都市ではseed/道路形状により変動するが、旧6本より概ね4倍程度以上の短距離routeになる。

### 14.2 車両数

1route:

- 3.2 km以上、またはstop sequenceが多い: 4台
- その他: 3台

### 14.3 駅フィーダー

Central/SubCenter向け専用feederも5 km以下へ短縮する。長い候補は中間stopを減らす。

### 14.4 運用

Busは通常道路交通へ参加し、実Agentを停留所で乗降させる。車両はバス営業所から出庫する。

---

## 15. タクシー

Taxi fleet target:

```text
round(population / 800)
```

を18～120台へclampし、VehicleStore空き容量も上限とする。

trip distance 350 m未満はtaxi選択対象にしない。

住民のtaxi選択確率はwealth、夜間、trip distance、surface transit fallback等で変わる。Visitorはhotel/tourism等のpurposeに応じて別確率を持つ。

Taxi phase:

```text
idle
to-pickup
boarding
occupied
alighting
```

boarding/alightingは各4秒。

# 在来鉄道

## 16. 鉄道計画

標準構成は幹線3路線 + 必要に応じた副都心支線。

Station座標:

- `plannedX/Z`: TOD/計画位置
- `x/z`: 駅設備/physical context
- `roadNode`: 道路接続点
- `line.path`: 列車走行/線路描画の基準

line.pathは可能な限りRoad A* node列を使う。

### 16.1 郊外駅間隔

`RailRuralStationSpacing` により駅間隔を中心部から郊外へ拡大する。

locality factor:

```text
中心: 1.0
外縁: 2.0
```

支線側もlocal spacingを参照する。

---

## 17. 在来鉄道運行

主要現行仕様:

- 幹線: Local / Rapid / Limited
- 支線: Local
- 右側通行
- 方向別block/signal
- passing loop / siding
- 15秒time quantum
- terminal / depot
- service外や出庫時のdeadhead
- 終端platform最低270 m
- siding offset 10.4 m
- 実列車への旅客乗降
- 最大1回transfer

列車編成位置は単一running distanceを基準にし、各carを同じsmoothed lineからsampleする。

---

## 18. 駅・旅客設備

Visible station architectureは最終smoothed railへ追従する。

主な設備:

- platform slab/canopy
- benches
- vending machines
- emissive fluorescent fixtures
- real station lights
- ceiling-hung departure boards
- stairs/access
- passenger waiting points

発車案内boardは最大3列車を表示し、実運行のstop判定と時刻を参照する。

Rail passengerはteleportせず、street → station access → platform → train → platform → streetを物理的に移動する。

# 外部鉄道・描画・UI

## 19. 外部接続高速鉄道

在来鉄道と別subsystemとして運用し、中央駅への外部来訪者交換、running train、dwell/schedule、passenger loadを持つ。

## 20. 描画

主要方針:

- pedestrian/vehicle distance LOD
- static road/station geometry

森林と街路樹は最終道路clearance filterを受ける。

## 23. 現行の制約・技術的負債

- 金銭、価格、企業利益、賃金等の一般経済モデルは未実装。
- office/commercialの勤務効率は表示できるが、物理service outputには未接続。
- RailRendererは運行と描画の責務を混在している。
- prototype patch/import順に依存するruntime tuningが多い。
- `src/version.ts` は版番号とruntime tuning import入口を兼ねる。
- Taxi passengerはbase AgentState互換のためbus系stateを再利用している。
- 後段生成tuningが先行生成結果を再分類/削除する箇所があり、将来的には統一reservation modelが望ましい。
