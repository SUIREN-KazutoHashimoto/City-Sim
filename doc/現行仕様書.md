# City-Sim 現行仕様書

## 1. 文書の位置付け

- 対象: `develop` ブランチの現行実装
- 更新基準日: 2026-08-24
- 目的: 現在動作している City-Sim の仕様を、都市生成・交通・鉄道・旅客・描画・UIまで横断して一冊で確認できるようにする。
- 本書を「現行仕様の正本」とする。
- `CityGeneratorV2_Phase*.md` は開発履歴であり、現行仕様と矛盾する場合は本書を優先する。

ソースコードが本書より新しい場合はソースコードを最優先とし、機能変更時は本書も更新する。

| 都市面積 | 100 km² |
| 都市一辺 | 10 km |
| 市街地目標比率 | 0.40 |
| 基準街区 | 90 m |
| 初期人口 | 50,000 |
| Agent capacity | 60,000 |
| Vehicle capacity | 30,000 |
| 副都心数 | 3 |
| 幹線道路間隔 | 900 m |
| Collector間隔 | 360 m |
| Industrial比率 | 0.08 |
| Park比率 | 0.055 |
| 鉄道 | 有効 |
| 幹線鉄道路線 | 3 |
| 駅間隔基準 | 525 m |
| 駅影響半径 | 900 m |

Seed が `random` の場合、起動時に実Seedを生成する。都市の静的生成はSeed再現を意図するが、Agent等の一部に `Math.random()` が残るためシミュレーション全体の完全決定論は保証しない。

## 3. システム構成

```text
main.ts
  ├─ CityConfigLoader
  ├─ World
  │   ├─ SimulationClock
  │   ├─ AgentStore / NeedSystem / UtilityBrain
  │   ├─ CityGenerator / CityPlanning / BlockParcelLayout
  │   ├─ RoadNetwork / SidewalkNetwork
  │   ├─ TrafficSystem / SignalSystem
  │   ├─ BusSystem / LogisticsSystem
  │   └─ RailPassengerIntegration
  ├─ RailNetworkPlan
  ├─ RailRenderer
  │   ├─ timetable / block / dispatch
  │   └─ railway enhancement modules
  ├─ EnhancedRenderer / InstancedRenderer
  ├─ TrainLiveryOverlay
  ├─ Inspector / Dashboard / PerformanceMonitor
  └─ FirstPersonController
```

大量Agent/VehicleはSoA TypedArrayを基本とする。Cross-Origin Isolationが利用できる環境ではSharedArrayBufferを使用し、Agent/Pedestrian/POI系Workerと共有する。

## 4. 都市生成

### 4.1 都市計画

都市生成では単一のノイズ値だけでなく、都市計画レイヤを持つ。

代表的なDistrict:

- CBD
- Commercial
- MixedUse
- ResidentialHigh
- ResidentialLow
- Industrial
- Logistics
- Civic
- Park

`urbanScore`、`landValue`、`density`、中心影響、副都心、産業・物流配置などを分離して扱う。

### 4.2 道路階層

道路階層は概ね次の順序とする。

```text
Highway > Arterial > Collector > Local > Path
```

道路は都市計画・街区形成の骨格となる。鉄道は道路網から完全に独立した直線網ではなく、道路回廊を利用しつつ細かなジグザグを簡略化する。

### 4.3 街区・Parcel

街区はBlock/Parcelへ分割し、間口、奥行、setback、駐車、Parcel統合、開発強度を持つ。建物用途と外観アーキタイプは分離する。

### 4.4 公共施設・公園

生成対象には学校、病院、大学、市役所、警察、消防、ショッピングモール、スーパー、ホテル、ガソリンスタンド、スタジアム、公園等を含む。

## 6. 鉄道計画

### 6.1 路線

標準設定では幹線3路線を生成し、副都心への支線を追加できる。駅間隔基準は525m、TOD影響半径は900m。

### 6.2 道路回廊型アラインメント

通過駅は道路網へ対応させ、駅間は道路A*結果を「回廊」として利用する。A*の細かな折れ点をそのまま線路にせず、回廊内で簡略化して長い直線と必要なカーブへ変換する。

概略許容幅:

- 幹線: 道路回廊から約38m
- 支線: 約28m

終端駅は道路中央を避けて土地側へ引き込み、道路接続点から滑らかな専用アプローチで接続する。

### 6.3 複数路線駅

共有駅では路線ごとに高さを分離する。幹線レベルは概ね4.8mずつ上下差を付ける。共有駅・副都心駅は乗換駅として扱う。

## 7. 列車運行

### 7.1 右側通行

幹線複線は右側通行を標準とする。

RailRendererではpath正方向に対して正offsetが左側のため:

```text
進行方向 +1 → lane -1
進行方向 -1 → lane +1
```

停車中は到着時のlane/ホームを保持し、折返し後の正規線への切替は発車時に開始する。これにより停車中の別ホームへの瞬間移動を防ぐ。

### 7.2 閉塞

1駅間を片方向3閉塞に分割する。幹線複線では上下線を分離するため、1駅間あたり実質6方向別閉塞となる。

### 7.3 信号現示

信号機は「信号直後の閉塞」を制御対象として表示する。

```text
直後閉塞が使用不可       → 赤
直後は空き、次閉塞が不可 → 黄
2閉塞先まで空き           → 緑
```

同方向・同線路で当該列車用に確保された予約は、その信号に対して進行可能扱いとする。

ホーム内に閉塞境界が存在しても制御は有効だが、ホーム中央の物理信号機は描画しない。ホーム内は仮想信号扱いとする。

### 7.4 反対線運転

渡線による反対線使用は遅延・デッドロック回復用の例外運転。

- 特急: 12秒待ち以降
- 快速: 30秒待ち以降
- 普通: 75秒待ち以降
- recovery train: 即時検討可能

反対線へ入る場合、対象駅間の3閉塞すべてが利用可能であることを要求する。反対線運転列車がいる駅間には対向する正規列車を進入させない。

### 7.5 種別・編成

幹線では普通・快速・特急を運転する。

概略Fleet生成:

- 普通: 駅数×0.50
- 快速: 駅数×0.30（幹線、4駅以上）
- 特急: 駅数×0.10（幹線、6駅以上）
- 予備普通: 普通基本数の約40%

編成:

- 幹線普通: 4両
- 支線普通: 3両
- 快速/特急: 5両

### 7.6 運行時間

- 営業開始: 05:00
- 最終出発基準: 23:30
- 朝ピーク: 07:00–09:30
- 夕ピーク: 17:00–19:30

予備普通はピーク帯で運用し、営業時間外・ピーク終了時は終端で入庫する。

### 7.7 速度制御

カーブ、渡線、分岐、待避線、終端ファンに速度制限を持つ。代表値:

- 渡線: 約30km/h
- 分岐: 約40km/h
- 待避線: 約54km/h

制限地点の直前で急減速せず、将来の制限速度を先読みして制動可能速度を算出する。

### 7.8 列車運動

編成全体は1つの `run.distance` を基準にし、各車両をそこから逆算する。車両ごとに独立した追従制御を行わないため、カーブや速度変化でも編成の伸縮を防ぐ。

## 8. 終端駅・車両基地

### 8.1 終端駅

終端駅は4線ファンを持つ。代表offset:

```text
-9.5, -1.9, 1.9, 9.5m
```

ファン長は約150m。停車ホームはdwell中固定し、発車後に正規の右側本線へ収束する。

### 8.2 車両基地

車両基地は実際の `RailStationKind.Terminal` にのみ生成する。同一物理終端駅を複数路線が共有する場合は1基地へまとめ、幹線を優先する。

現行基地:

- 8留置線
- 留置線間隔 4.4m
- 奥行 約260m
- 短い共通入出庫線 + 横長ラダー

支線列車も必要に応じて最寄りの実終端基地を共有する。留置位置は基地内ローカル順位で割り当てる。

## 9. 鉄道旅客

### 9.1 経路選択

鉄道候補は概ね520m以上の移動で検討する。乗車駅・降車駅候補は各端760m以内から最大6駅を選ぶ。

対応経路:

- 同一路線直通
- 最大1回乗換

概算所要時間では徒歩1.45m/s、列車19m/s、初期待ち105秒、乗換145秒を使用し、鉄道見込み時間が徒歩の92%以下の場合に鉄道を採用する。

### 9.2 鉄道通勤需要

鉄道導入前の人口生成では非自動車世帯の勤務先が近距離へ偏りやすいため、駅勢圏の非自動車就業者の一部を別駅勢圏の勤務先へ再配置する。

- 自宅/勤務先駅勢圏: 原則500m以内
- 原則4駅以上離れた駅を候補
- 通勤距離は1.5km級以上を優先
- 対象候補の約80%を需要補正対象

起動負荷を避けるためWork POIは駅別に一度だけ索引化し、Agentごとに全POI検索を行わない。

### 9.3 乗車動線

鉄道利用者は駅座標へ瞬間移動しない。

```text
街路徒歩
  ↓
駅入口
  ↓
階段/連絡通路
  ↓
ホーム
  ↓
WaitingTrain
  ↓
実際に停車中の列車へ乗車
```

ホーム到達前のAgentは列車へ乗れない。

### 9.4 降車動線

```text
列車
  ↓
ホーム
  ↓
駅内階段
  ↓
地上階段
  ↓
街路徒歩
```

乗換時は地上へ降りず、ホーム間の駅内動線を使う。

### 9.5 複数階駅の階段

複数路線駅は各ホームから直接地上へ降ろさない。

```text
上層ホーム
  ↓
1つ下のホーム
  ↓
…
  ↓
最下層ホーム
  ↓
地上
```

ホーム間階段は安全なホーム交点・踊り場を使い、線路・車両限界を斜め横断しない。地上接続では道路上で高度を下げず、ホーム高さの水平通路で道路外へ逃がしてから道路外側で階段を降ろす。

### 9.6 定員

旅客定員は現状の簡易モデルで1両120人。満員列車には新規乗客を乗せない。

列車Inspectorには次を表示する。

```text
乗客 n / 定員 m  混雑率 xx%
```

## 10. 駅・線路・列車の描画

### 10.1 駅外装

駅舎は内部をSolid Boxで埋めない。既存ホームの外周へ薄い部材として追加する。

- 腰壁
- ガラス窓帯
- 縦フレーム
- ファサード
- 薄い屋根
- 駅名サイン

中央の階段付近とホーム端には開口を残し、内部は実際に空洞・通行可能とする。

### 10.2 高架支持

駅柱・線路高架柱は道路占有を判定する。道路上へ直接柱を落とさず、安全な左右位置へ柱を逃がし、必要に応じて門型/横梁で支持する。

### 10.3 照明

- 線路保守灯: 約115m間隔
- 駅ホーム照明
- 列車前照灯: 先頭車端面の左右2灯
- 列車尾灯: 最後尾端面の左右2灯

列車灯は実車両のInstance Matrixから位置を取得するため、カーブで車体から浮かない。

### 10.4 ホーム案内灯

- 発車案内灯: 緑
- 接近案内灯: 橙点滅
- 接近判定: 停車予定列車が約280m以内

### 10.5 列車外装

列車は路線色帯と種別色帯を持つ。種別色の代表:

- 普通: 緑
- 快速: 橙
- 特急: 赤

## 13. 鉄道拡張モジュールの適用順

鉄道は現在、`RailRenderer` のコア実装に加えてPrototype Patch型の拡張モジュールを使用する。`TrainLiveryOverlay.ts` のimport順が意味を持つ。

```text
RailPlanningEnhancements
RailRendererEnhancements
RailDepotPlacement
RailRightHandOperation
RailSignalPlatformClearance
RailLightingAndIndicators
RailSupportClearance
RailStationArchitecture
PedestrianSignalOrientation
RailPassengerStationAccess
RailPassengerAutoAttach
  ├─ RailPassengerStairClearance
  ├─ RailPassengerGroundStairs
  └─ RailPassengerIntegration
RailPassengerVisualConsistency
RailPassengerDemand
TrainPassengerInspector
```

後段のPatchが前段のメソッドをラップ/上書きするため、import順を変更すると動作が変わり得る。

## 14. 既知の制約

- 鉄道旅客経路は直通または1回乗換まで。
- 列車定員は1両120人の簡易モデルで、座席/立席/扉別処理はない。
- 乗降は「ホームへ実Agentが移動し実列車へ乗る」が、扉位置・乗降時間・ホーム混雑流動は簡略化している。
- 駅内階段・駅舎は手続き生成の簡易構造で、実建築レベルの衝突判定は未実装。
- 車両基地への出入庫運転は営業本線運行より簡略化されている。
- 鉄道拡張がPrototype Patchチェーンになっており、import順依存がある。安定後はコア統合が望ましい。
- 静的都市Seedは再現を意図するが、全シミュレーションの完全決定論は未保証。
