# Machi-Sim 性能モニタ仕様

## 1. 目的

100 km²・数万人規模で、処理落ちを「simulation」「pre-render」「render」「GPU」へ分離し、さらにWorker/Agent/Ped/Traffic/Rail/A*等の原因へ掘り下げる。

**実装を正とし、本書は `PerformanceMonitor.ts` と現行scheduler/worker構成の要約とする。**

## 2. UI

Performance Monitorは常時右側へ固定表示しない。

現行UI:

- 初期状態: 非表示
- `P`: 表示/非表示
- 右下 `UI` launcher: GUIから表示/非表示
- 共通window shellでdrag移動可能
- `resize: both` でリサイズ可能
- position/size/visibilityをlocalStorageへ保存
- `×`で非表示

複数debug panelを同時表示した場合はユーザーが自由に並べられる。

## 3. Sampling

Performance Monitorは短周期で最新値をsamplingし、約60秒級の履歴graphを保持する。

主要トップレベル:

- **Frame**: requestAnimationFrame間隔
- **Pre**: WebGL render開始前のrail/visual/follow等main-thread処理
- **Render**: LOD、dynamic mesh sync、環境更新、WebGL submit等
- **GPU**: timer query利用可能時のGPU実行時間
- **SIM**: `World.stepBatchAsync` wall time

16.67ms / 33.33msを60FPS/30FPSの目安として見る。

## 4. Pre-render内訳

代表項目:

- RailOps: `RailFrameScheduler` が当該frameで進めたrail operations
- RailVis: reservation/mesh/signal/turnout/timetable等のrail visual同期
- RailBacklog: 未処理rail simulation seconds
- Livery: TrainLiveryOverlay
- Vehicle smoothing: VehicleVisualSmoother
- Other: follow、Dashboard等

`RailBacklog` が高倍率で継続増加する場合、rail側のCPU budgetに対して要求simulation量が大きい。

## 5. Rendering内訳

- LOD
- Agent sync
- Road vehicle sync
- Signal sync
- Lighting / environment
- WebGL submit

### 描画フィルターとの関係

`RenderFilterTuning` / `RenderFilterRailSplit` でcategoryを非表示にすると、GPU描画だけでなく一部dynamic visual syncも省略される。

したがってPerformance結果は次を区別する。

1. **通常性能測定**: 全表示
2. **simulation切り分け**: 建物/車/歩行者/rail等を必要に応じて非表示

Filter OFFでもsimulationは継続するため、SIM bottleneckの切り分けに利用できる。一方、filtered状態のRender値を通常画面性能として記録しない。

## 6. Simulation内訳

積み上げは可能な限りtop-level wall timeが重複しないよう分類する。

代表:

- Workers
- Agent decision/routing
- Pedestrian
- Traffic
- Bus
- Logistics
- Signals
- Activity/arrival
- Other

Worker内部計測はtop-level SIMへ重複加算するのではなく、原因診断用のsub-metricとして扱う。

## 7. Pedestrian診断

Pedestrian Workerの現行方式:

1. Shared job epoch変更で常駐Workerをwake
2. 前stepのused spatial cellsをsparse clear
3. current coordinatesをsnapshot
4. Worker barrier
5. linked-cell spatial indexを並列build
6. Worker barrier
7. Avoid + Move
8. 最後のWorkerがDONE epoch更新
9. main側は対応環境で `Atomics.waitAsync`、非対応時はmessage fallback

代表計測:

- Block preparation
- Worker wall
- Worker prep/snapshot
- Worker index
- Avoid+Move
- Barrier
- Wake
- Return
- DispatchGap / OtherGap
- rounds
- completion mode
- μs/ped/step

Spatial cellは8 m。都市全cellを毎step clearせずused cellだけをclearする。

## 8. POI診断

POI検索はカテゴリ別空間indexを使い、検索要求をbatch化してWorkerへ渡す。

代表項目:

- WorkerSearch
- MainSearch
- Parking
- Reserve/Release
- Activity+Arrival

POI静的情報はWorkerへ持たせ、occupancyはSharedArrayBufferで共有可能。最終reserve/releaseはCoordinator側で確定する。

## 9. A*診断

Walk A* / Vehicle A*について:

- total ms
- count
- max single-query ms

を確認する。

A* implementationの現行性能方針:

- 毎searchで全work arrayをfillしない
- touched nodeだけ初期化
- heap positionを持ちdecrease-keyをO(log n)
- static graph向け最大4096件級のLRU route cache
- routing start数へsimulation-step budget

Graphをruntime変更する機能を追加する場合はcache clear/invalidationが必要。

## 10. Traffic診断

TrafficSystemは全Road Edgeを無条件clear/sortせず、前/現stepでvehicleが存在するactive edgeを中心にoccupancy rebuildする。

`TrafficTurningTuning` はturn中だけvehicle free-road speed targetを一時capするが、IDM/signal/occupancyはbase TrafficSystemを使用する。

性能悪化時は「vehicle count増加」と「1 vehicle当たりTraffic cost」を区別する。

## 11. Rail診断

### RailFrameScheduler

Railはsimulation timeを1frame内で無制限消化しない。

現行方針:

- 低倍率は細かいstepを維持
- 高倍率ではtimeScaleに応じstep幅を拡大
- 1 RAFのrail step数を制限
- CPU budgetを超えたら打切り
- 未処理sim秒をRailBacklogへ繰越
- dynamic rail visualsはoperations stepごとではなくframe側でまとめて同期

確認項目:

- Rail input seconds
- Rail processed seconds
- Rail backlog seconds
- RailOps CPU
- Rail visual CPU
- step count / step seconds

## 12. Workload

処理時間だけでなく件数を見る。

代表workload:

- LOD別visible Agent
- LOD別visible Vehicle
- moving/waiting pedestrians
- driving vehicles
- building LOD counts
- simulation backlog
- worker count

「対象数が増えただけ」なのか「1件コストが悪化」したのかを分離する。

## 13. LOD / GPU Instancing

大量の建物、道路設備、Agent、Vehicle、Rail設備はGPU Instancingを基本とする。静的rail/station geometryはbuild時に作り、通常frameで再生成しない。

LODはcamera distance/follow状態等に応じvisible量を抑える。

## 14. Benchmark時の注意

比較条件を固定する。

最低限記録:

- seed
- city config
- population/capacity
- simulation speed
- camera/follow条件
- 描画フィルター状態
- 表示中debug window
- browser/実行環境

Performance Monitor自体を開くとDOM/canvas描画負荷が増えるため、純粋な通常UI FPSを測る場合はMonitorを閉じた結果も取る。

## 15. UI Window Managerとの関係

Performance panelのposition/sizeは `UiNoiseReduction` が外側shellで管理する。`PerformanceMonitor` 内部の可視flagとWindow Managerのdesired visibilityを同期するため、`P`とGUIのどちらで操作しても状態を一致させる。

Window layout persistence:

```text
city-sim-window-layout-v2
```

描画filter stateとは別保存。

## 16. 性能変更時のルール

性能最適化を入れる場合:

1. simulation semanticsを変える変更と純性能変更を分ける。
2. Before/Afterを同Seed・同表示条件で比較する。
3. Top-level SIM/Renderだけでなくworkload件数も比較する。
4. 新しいWorker待ちやcacheを入れる場合はfailure/fallback pathを残す。
5. Graph/cacheがstatic前提なら、その前提を壊す機能追加時にinvalidationを設計する。
6. 新metricを追加したら本書とUI labelを同期する。
