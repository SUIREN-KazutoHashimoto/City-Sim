# 性能モニタ仕様

## 1. 目的
100km²・数万人規模で、処理落ちの原因をレンダリングとシミュレーションの双方からリアルタイムに切り分ける。

## 2. 表示
画面右側に PERFORMANCE パネルを表示する。Pキーで表示/非表示を切り替える。
サンプリング間隔は250ms、履歴は最大240点（約60秒）。

### Frame timing
- Frame: requestAnimationFrame間隔
- Render: LOD更新、Agent/Vehicle/Signal同期、環境・照明更新、WebGLコマンド発行のCPU時間
- GPU: EXT_disjoint_timer_query_webgl2が利用可能な場合のGPU実行時間
- SIM: World.stepBatchAsyncのwall time
- 16.67ms / 33.33msの目安線を表示

### Rendering内訳
- LOD
- Agent sync
- Vehicle sync
- Signal sync
- Lighting / Environment
- WebGL submit

### Simulation内訳
積み上げグラフは重複しないトップレベル時間を表示する。
- Workers: Agent Worker + POI Search Worker。Ped WorkerはPed内のネスト時間として扱う
- Agent: Needs（同期fallback時）+ Utility判断 + trip開始/モード選択 + routing呼出し
- Ped: pedestrian block構築 + 歩行準備 + Ped Workerのspatial index / avoidance / movement
- Traffic
- Bus（update + onboard同期）
- Logistics
- Signals
- Activity: 車両到着処理 + Engaged活動/退出確定
- Other: batch総時間から上記を引いた残余

### Ped詳細
Pedは以下を個別表示する。
- Block: 横断歩道付近のpedestrian block / vehicle block構築
- MainIndex: 同期fallback時のみ使用する従来SpatialHashGrid再構築。Worker利用時はほぼ0になる
- Path/Signal: 目標ノード、信号待ち、到着判定、base desired vector生成
- WorkerWall: `PedestrianWorkerPool.flush()` のmain threadから見たwall time
- Worker Prep: 前stepで使用したspatial cellのsparse clear + 現step座標snapshotの各Worker最大時間をstep単位で積算
- Worker Index: linked-cell spatial indexの並列構築時間
- Avoid+Move: neighbor探索、separation/avoidance、速度・位置・向き・energy更新時間
- Barrier: Worker間の `Atomics.wait/notify` バリア待機時間
- Wake: main threadがjob epochを更新してから、最も遅いPed Workerが実行を開始するまでの概算待ち時間
- Return: 最後のPed Workerが完了epochを更新してからmain thread側の`flush()`継続が再開するまでの概算待ち時間
- OtherGap: `DispatchGap - Wake - Return`。時刻計測分解で説明できない残余
- DispatchGap: WorkerWallからWorker内部critical-path時間を引いた値。main/Worker間のスケジューリング、完了通知、ブラウザtask/microtask実行待ち等の概算
- rounds: 1 batch内で実際にPed Workerへdispatchした回数。通常はsimulation step数に近い
- completion mode: `atomics` は`Atomics.waitAsync`完了待ち、`message` は非対応ブラウザ向け`postMessage` fallback
- µs/ped/step: PED totalを「現在の歩行者数 × batch内step数」で割った概算1歩行者1stepコスト

Pedestrian WorkerはSharedArrayBuffer上のAgent SoAを直接更新する。Coordinatorは経路カーソル、信号、バス/車への乗り換え、POI到着など状態遷移だけを担当する。
Worker側は各stepの開始時点の歩行者座標をsnapshotへコピーし、そのsnapshotからlinked-cell spatial indexを構築する。その後、複数Workerが同じsnapshotを読みながら近傍分離・回避と移動積分を並列実行するため、別Workerがlive座標を書き換えても同一step内の近傍判定は変化しない。

Spatial indexのセルサイズは8m。10km級市街地でも全セルを毎step初期化せず、前stepで使用したセルだけをクリアするsparse clear方式とする。使用セル一覧自体もSharedArrayBufferで共有する。

第3段階ではmain threadが `Index → await → Move → await` と2回同期していた構造を廃止し、index構築とmovementをWorker内部barrierで連結した。

P0最適化ではさらに、各stepで全Ped Workerへ `postMessage` を送る方式を廃止した。Ped Workerは初期化後にSharedArrayBuffer上のjob epochを `Atomics.wait` して常駐し、main threadはjob ID / active count / move count / dtを書き込んだ後、job epochを更新して `Atomics.notify` する。

各stepのWorker内部処理:

1. job epochの変更で常駐Workerをwake
2. 使用済みcellのsparse clearと座標snapshotをWorker分割して実行
3. `Atomics.wait/notify` barrier
4. `Atomics.exchange` を用いてlinked-cell indexを複数Workerで同時構築
5. `Atomics.wait/notify` barrier
6. Avoid + MoveをWorker分割して実行
7. 最後のWorkerが共有DONE epochを更新し、main側の`Atomics.waitAsync`をwake

再計測でmain→Worker側を`Atomics.notify`へ変更してもDispatchGapがほぼ一定だったため、次段階ではWorker→main側のstep単位`postMessage`もhot pathから除外した。対応ブラウザではmain threadが共有DONE epochを`Atomics.waitAsync`で非同期待機する。`Atomics.waitAsync`非対応環境だけは従来の完了`postMessage`へfallbackする。

`Atomics.wait` はDedicated Worker内だけで使用し、browser main threadをブロックしない。main threadの完了待ちは`Atomics.waitAsync`なので同期blockしない。

横断歩道Block判定では、従来毎step `SidewalkNetwork.edgeBetween()` を全歩行者に対して実行していたが、現在のpath cursorに対応する「次の横断road node / axis」を経路設定・cursor更新時にキャッシュし、step中はキャッシュ値だけを見る。P1/P2最適化ではBlock配列の全fillもやめ、前stepで立っていたdirty nodeだけをclearする。

### POI詳細
POIは以下を個別表示する。
- WorkerSearch: POI Search Worker Poolのbatch wall time
- MainSearch: Coordinator側で実行されたfindBestの合計ms / 件数
- Parking: findNearestFreeの合計ms / 件数
- Reserve/Release: occupancy変更処理の合計ms / 件数
- Activity+Arrival: 施設滞在・退出、車両到着後処理

POI検索の静的データはWorkerへ複製し、occupancyのみSharedArrayBufferで共有する。reserve/releaseは競合回避のためCoordinator側で確定する。
Shared occupancyの更新はAtomics.store、Workerからの読み出しはAtomics.loadを使用する。

POI Worker内のカテゴリ別空間索引はnested `Map<number, Map<number, number[]>>` ではなく、都市範囲に合わせたdense cell head + linked listを使用する。200mセルの100km²都市ではhead配列は十分小さく、query中のMap lookupとbucket object走査を避けられる。

RuntimeのPOI検索要求はJS object配列をそのままstructured cloneせず、`category/x/z/wealth` をTypedArrayへ詰めてWorkerへtransferする。Worker結果もInt32Arrayをtransferして返す。

### A*診断
A*は親フェーズ内に含まれるため積み上げには二重計上しない。別途、以下を表示する。
- Walk A*: 合計ms / 件数 / 最大1件ms
- Vehicle A*: 合計ms / 件数 / 最大1件ms

A*のwork arrayは検索ごとの全配列 `fill()` を行わず、前回検索でtouchしたnodeだけを初期化する。open heapはnode→heap positionを保持してdecrease-keyをO(log n)で処理する。
道路・歩道graphはruntime中に静的であるため、start/goal node pairに対して最大4096件のLRU route cacheを持つ。同一graphを動的に変更する実装を追加する場合はcache invalidationまたは`clearCache()`を必須とする。

Routingは1 simulation stepで無制限に開始せず、Coordinator側でbudgetを設ける。これにより通勤時刻境界などでA*が同一stepへ集中することを避ける。

## 3. Workload
- LOD0/1のVisible Agent数
- LOD0/1のVisible Vehicle数
- 移動中/バス待ちの歩行者数
- Driving状態の車両数
- 建物LOD0/1/2/3件数
- Simulation backlog

処理時間だけでなく処理件数を併記し、単純なオブジェクト増加と1件あたり処理コストの悪化を切り分ける。

## 4. POI検索最適化
POIRegistryはカテゴリ別SpatialHashGridを使用する。
従来の拡大検索では300→800→2000mの各段階で内側セルを再走査していたため、queryExpandingを追加し、前段で走査済みのセルを除外して外周セルだけを追加走査する。

RuntimeのUtilityBrainは、行動カテゴリ決定と施設検索を分離する。
Home/Workのような直接目的地はCoordinatorで即時確定し、Food/Retail/Leisure等の検索が必要なAgentだけを最大512件単位でPOI Search Worker Poolへまとめて送る。

Workerが返した候補は最終確定ではない。beginTrip時にCoordinatorがreserve可否を再確認し、満員の場合は既存fallback検索を行う。

## 5. Coordinator走査削減
Agent WorkerはEngaged終了条件を検出したAgentについて、従来の`activityExit` flagに加え、SharedArrayBuffer上のexit ID queueへAgent IDを積む。Worker batch完了後、Coordinatorは全Agentを再走査せずqueueに載ったAgentだけPOI occupancy/stockを確定する。

バス待ちAgentは `stopId:routeId` 単位のqueueへ登録する。バス到着時は全AgentからWaitingBusを検索せず、該当queueだけを消費する。queue要素は乗車時に状態を再検証するため、将来別経路で状態変更が入ってもstale entryを安全にskipできる。

TrafficSystemのoccupant rebuildは全Road Edgeを毎stepclear/sortせず、前stepまたは現stepで車両が存在するactive edgeだけをclear/sortする。Driving vehicle自体の走査は維持し、IDMの意味は変更しない。

## 6. 計測負荷への配慮
Agentや歩行者を1個体ごとにperformance.now()で計測しない。
World.stepCore / stepCoreAsyncのフェーズ境界をラップして一括計測する。
Ped Worker内部はWorker単位のフェーズ時間だけを計測し、個体単位のperformance.now()は行わない。各フェーズ表示は各Workerの最大時間をstepごとに積算した診断値である。
POIのfindBest/findNearestFree/reserve/releaseは呼出単位で集計するが、個体全処理を分解する計測は行わない。
A*のみ経路探索リクエスト単位で計測する。
PerformanceパネルのCanvas再描画は4Hzに抑える。

## 7. 注意事項
GPU時間はWebGL2のEXT_disjoint_timer_query_webgl2が利用できない環境ではn/aとなる。
SIM内のA*値とPOI MainSearch/Parking/Reserve値、Ped Worker内部値は親フェーズにも含まれるネスト計測であり、積み上げSIM時間へ追加してはならない。
POI Worker / Pedestrian WorkerはSharedArrayBufferが利用できない場合は無効化され、同期処理へfallbackする。
同期 `World.step()` では従来のMain Thread SpatialHashGridを利用し、非同期 `stepBatchAsync()` のPed Worker経路だけWorker spatial indexへ切り替える。

Persistent Ped Workerはinit後に`Atomics.wait` loopへ入るため、step処理用の追加`postMessage`を受け取る設計へ戻してはならない。停止はWorker.terminate()で行う。
