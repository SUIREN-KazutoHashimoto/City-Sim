# 2. 起動・更新系

## `src/main.ts`

主責務:

- config読込後のWorld/Renderer構築

- SimulationClock進行

- 通常固定stepを使用。
- 高倍率時は最大substep数を制限。
- `totalSeconds`, `hourF`, `dayPhase` 等を提供。

# 5. World

## `src/world/World.ts`

主責務:

- Agent action lifecycle
- POI reserve/release
- trip開始
- walk/drive/busの状態遷移
- Traffic/Bus/Logistics/Signalとの配線
- activitySnapshot
- Worker batch coordination

鉄道導入後はPrototype Patchでtrip開始/歩行更新/活動統計の一部を拡張する。

---

## `src/world/RailPassengerIntegration.ts`

鉄道旅客統合の中心。

### `RailTransitProvider`

```ts
boardingTrains()
passengerTrainPosition(id)
passengerStationAccesses(stationId, lineId, direction)
```

WorldはこのAPIを通してRailRendererへアクセスする。

### PassengerData

WorldごとにWeakMapで保持する。

```text
provider
boardStation[]
alightStation[]
line[]
nextLine[]
finalStation[]
train[]
access Map
routes Map
visual.active[]
visual.y[]
```

### `chooseRailTrip()`

- 520m未満はrail候補外。
- 起点/終点それぞれ760m以内の駅を最大6件。
- 直通を評価。
- 1回乗換を評価。
- WALK=1.45m/s, TRAIN=19m/s, WAIT=105s, TRANSFER=145s。
- rail seconds <= walk seconds × 0.92 なら採用。

### 駅構内route

`RailWalkRoute` は3D point列を持つ。

`stepRoute()` はx/zだけでなくvisual Yも補間し、階段移動を3Dで表現する。

route完了時:

- `finish='wait'` → `WaitingTrain`
- `finish='exit'` → 通常徒歩へ復帰

### 乗車

`WaitingTrain` のAgentについて実際の `boardingTrains()` を確認し、対象line/方向/降車駅へ停車する列車へだけ乗せる。

### `OnTrain`

Agentの論理位置を列車位置へ追従する。地上歩行者Meshは非表示にする。

### 降車/乗換

降車時はplatform accessを取得し、ホーム上へAgentを出してから駅内routeを開始する。

乗換がある場合は地上へ出ず次ホームへ移動する。

## `src/world/RailPassengerDemand.ts`

通常 `World.populate()` の後段で鉄道通勤ODを補正する。

### 性能上の重要点

Agentごとに `POI.findBest()` を実行しない。

起動時に:

```text
Work POI all()
  → nearest station
  → Map<stationId, workPoiIds[]>
```

を一度構築する。

### 対象

- 非自動車
- Unemployed/Retiree以外
- 駅500m圏
- hash選択で約80%
- 原則4駅以上離れた駅勢圏

不正なStation/POI ID・座標はAgent単位でskipし、起動全体を落とさない。

---

## `src/world/RailPassengerMetrics.ts`

`OnTrain` Agentを列車位置へ対応付け、trainId別人数Mapを毎step更新する。

列車位置を2mセルで索引化し、全Agent×全列車の総当たりを避ける。

公開API:

```ts
World.railTrainPassengerCount(trainId)
```

# 7. RailRenderer コア

## `src/rendering/RailRenderer.ts`

現状、描画だけでなく鉄道運行状態も所有する。

主要状態:

```text
smoothLines
lineY
trainRuns
blocks
blockOccupancy
blockReservations
routeReservations
plannedRoutes
railSignals
turnoutIndicators
RailTimetable
```

### `TrainRun`

主要フィールド:

- lineId / service / carCount
- direction / lane / previousLane
- speed / distance
- currentStationIndex / originStationIndex / nextStationIndex
- dwellRemaining
- scheduledDepartureAt / scheduledArrivalAt / arrivalDelaySeconds
- state
- blocked / caution
- reserve / retireAtTerminal
- depot fields

### 重要不変条件: scalar distance

列車の運動は `run.distance` を唯一の編成位置基準とする。

各車両pose:

```text
run.distance
  + consist内car offset
  → front/rear bogie sample
  → car pose
```

**車両単位の独立追従/PD補正を追加しない。**

これが編成の滑らかな運動と車間固定を維持する重要条件。

### 閉塞

`BLOCKS_PER_INTERVAL = 3`。

幹線はlane -1/+1を別blockとして生成する。

### サービス

RailRenderer coreは普通/快速/特急、営業時刻、peak reserve等を管理する。

## 8.3 `RailDepotPlacement.ts`

旧「全路線端に基地」を上書きする。

### terminalHosts()

- `RailStationKind.Terminal` のみ対象。
- shared stationIdをdedupe。
- trunk host優先。

### depotHostForRun()

自路線端がreal terminalならそれを使用。そうでなければ距離 + 高さ差penaltyで最寄りreal terminalを共有する。

### depotSlotForRun()

同一hostへ割当てられるtrainRunsだけをid順に並べ、host-local rankからtrack/slotを決定する。

### Yard constants

```text
tracks 8
gap 4.4m
track end 260m
```

---

## 8.4 `RailRightHandOperation.ts`

### rightHandLane()

```ts
return -direction
```

### `rebuildDispatchReservations()`

停車中laneを変更しない。到着ホームをdwell中保持する。

### `chooseRoutePlan()`

正規右側線を優先し、例外時のみ反対線候補を追加する。

reverse running:

- limited >=12s wait
- rapid >=30s
- local >=75s
- recovery immediate

対象駅間の全3block availabilityを要求する。

### `enterPlannedRoute()`

実際のlane transitionは発車時に開始する。

---

## 8.5 `RailSignalPlatformClearance.ts`

Rail signal buildを上書きし、platform centerから `platformLength/2 + 2m` 内の物理信号を生成しない。

Block自体は削除しないため運転保安は維持する。

---

## 8.6 `RailLightingAndIndicators.ts`

### signalAspect()

- signal.blockId unavailable → red
- signal.blockId clear / nextBlock unavailable → yellow
- both clear → green

同方向同laneのcompatible reservationは許容。

### track lights

spacing ≈115m。

### platform indicators

- departure green
- approach orange blink
- approach distance ≈280m

### train lamps

train body instanceのfirst/last matrixを取得し、車体端面へ左右2灯ずつ配置する。

`run.x ± consistLength/2` のような直線近似を使用しない。

---

## 8.7 `RailSupportClearance.ts`

Rail/Station supportの旧直下柱描画をmaterial colorで抑制し、道路回避型支持を再生成する。

道路Geometryをspatial cellへcacheする。

柱candidateが道路/交差点内なら:

- rail normal axis
- rail tangent axis
- occupying road normal

を候補に左右安全位置を探索する。

安全pairがあればportal beam、なければそのsupportをskipする。

---

## 8.8 `RailStationArchitecture.ts`

`buildStations()` 後に薄い駅外装を追加する。

部材:

- lower wall
- transparent glass
- fascia
- vertical frame
- roof cap
- sign

駅内部はSolid volumeで埋めない。

中央階段部・ホーム端にgapを確保する。

---

## 8.9 `PedestrianSignalOrientation.ts`

歩行者信号をvehicle signal facingから分離し、対応crosswalk方向へ向ける。横断歩道両端に向かい合う灯器を配置する。

# 9. 駅アクセス

## `RailPassengerStationAccess.ts`

駅ごとのentrance / stair / concourse / platform landing / platform waitをTransit Providerへ公開する基本実装。

## `RailPassengerStairClearance.ts`

複数路線駅のホーム間階段を安全化する。

- levelをlineTrackYでgrouping。
- 上層から直下levelだけへ接続。
- platform center line同士の安全な交点を使う。
- 長い1本の斜め階段で線路を横断しない。
- 同一駅/level/sideで重複階段を生成しない。
- 安全connectionが取れなければ無理なfallback stairを生成しない。

## `RailPassengerGroundStairs.ts`

複数路線駅の最下層→地上を上書きする。

重要条件:

**道路上では高度を下げない。**

```text
platform
  → same-height bridge across road space
  → outside roadway
  → stair down parallel to road/rail
  → entrance
```

sidewalk offsetは概ね `max(platform outer + margin, roadHalf + 3.6m)`。

# 13. Performance

`性能モニタ仕様.md` を正とする。

現行設計で特に重要な性能条件:

- RailPassengerDemandはpopulate時にAgent×POI総当たりをしない。
- RailPassengerMetricsはtrain spatial indexを使う。
- Pedestrian WorkerはShared snapshot + linked cell indexを使う。
- static rail/station geometryはbuild時生成し、毎frame再生成しない。

# 14. 変更時に守る不変条件

## 14.1 列車運動

**run.distanceを唯一の編成位置基準として維持する。**

車両個別追従を導入しない。

## 14.2 停車ホーム

dwell中に次進行方向へlaneを先行変更しない。

lane changeはdeparture plan確定後。

## 14.3 信号

物理信号を非表示にしてもblock/route reservationは削除しない。

## 14.4 駅階段

- road上でground stairを降下させない。
- rail vehicle clearanceを横切る長い斜めstairを生成しない。
- multi-level stationはadjacent level接続。

## 14.5 駅外装

内部をsolid boxで埋めない。旅客route/階段/ホームを塞がない。

## 14.6 Patch順

新規RailRenderer patch追加時は、既存original methodをどの時点でcaptureするかを確認する。

Patch importを並べ替えるだけでも挙動が変わる可能性がある。

# 15. 既知の技術的負債

- RailRendererがrenderingとrail operationsの両責務を持つ。
- Prototype Patchチェーンが長く、import順依存。
- rail passenger sidecar dataとAgentStoreの境界が暗黙的。
- station architecture/accessはprocedural prototype段階。
- depot entry/releaseは本線block運転と比べ簡略化。

安定後の整理候補:

1. RailOperations / RailRenderingの分離。
2. Enhancement modulesをcoreへ段階統合。
3. Station modelを明示データ化し、RendererとPassengerが同じstation geometry modelを参照。
4. Passenger rail fieldsの専用Store化。
5. Rail routingを複数回乗換対応グラフへ拡張。
