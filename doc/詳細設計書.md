## 1. 目的

## 3. Config bootstrap

`CityConfigLoader`は:

```text
DEFAULT_CONFIG
  <- raw top-level
planning:
  DEFAULT_CITY_PLANNING <- raw planning
power:
  DEFAULT_POWER_CONFIG <- raw power
```

でmergeし、各fieldを個別検証する。

`public/config/city.json`が現行標準起動値。コードdefaultとJSON値が異なる場合、通常起動ではJSON値が優先される。現行ではAgentStore default 60,000に対し、標準JSONは120,000を指定する。

## 4. Generation patch chain

### 4.1 Rural industry / farm

`RuralIndustryAndDepotTuning`はfleet depotsとproduction siteを生成する。

Production kind:

```ts
'farm' | 'raw-factory' | 'processor' | 'assembler'
```

Depot kind:

```ts
'taxi' | 'bus' | 'freight'
```

`AgriculturalEstateTuning`はfarmをmulti-block estateへ変換し、field extentとwarehouse/logistics sourceを分離する。

### 4.2 Final refinement

`CityGenerationRefinement`はstation clearance、farm field expansion、park trim等を後段で適用する。RetireしたBuildingに関係するPOI/facility/production registryも同期する。

### 4.3 Power facility generation

`PowerFacilityGeneration`はCityGeneratorの生成結果をPower facilityへ変換する。

候補除外:

- `city.facilities`のBuilding
- supply-chain production Building
- taxi/bus/freight depot Building
- 既に`infrastructureLabel`を持つBuilding
- Park district

優先選定:

- thermal / solar: Industrial/Logistics、Factory/Warehouse、十分なsite area
- external: gate付近、Industrial/Logistics
- substation: logical target付近、低層Building

変換:

```text
disable original Building POIs
→ building.category = Work
→ archetype/roof/floorsをroleに合わせて正規化
→ infrastructureLabel / powerFacilityKey / Roleを付与
→ Work POIを同じbuildingIdで新規登録
→ frontage側のnearest road nodeを記録
```

Generation roster targetは:

```ts
max(minimum, ceil(maxMw / 100 * staffPer100Mw))
```

でBuilding Work POI capacityを決める。Thermal minimum 8、solar minimum 2。

## 5. Workplace attendance

`WorkplaceProductivityTuning`はWork POIごとに以下をcacheする。

```text
present
onDuty
scheduled
assigned
capacity
efficiency
initialized
```

一般職場のphysical presence:

```ts
scheduled
&& state === AgentState.Engaged
&& goalPOI === work
```

一般職場では`onDuty = present`。

### 5.1 Lifeline check-in

Constants:

```text
LIFELINE_SHIFT_HANDOVER_GRACE_SEC = 45 * 60
LIFELINE_STARTUP_GRACE_SEC = 60 * 60
```

Lifeline workerがphysical presenceを満たした時、そのAgentについて:

```text
workPoiByAgent = work
shiftStartByAgent = current shift start
```

を記録する。同じWork POI・同じshift startであれば、physical presenceを離れても`onDuty`を維持する。

`onDuty`条件:

```text
scheduled
&& (checkedInSameShift || handoverGrace || startupGrace)
```

Lifeline efficiency:

```text
attendance = clamp(onDuty / concurrentStaff, 0, 1)
efficiency = attendance * buildingPowerOperationalFactor
```

一般workplaceは`present / capacity`を使う。

## 6. Workforce coverage

Lifeline workforceは通常workforce shortageより優先して補完する。

重要semantic:

- roster target = facility Work POI capacity
- rosterを3 shifts分に機械的に3倍しない
- three shiftsは同じrosterをscheduleする
- 100% operational target = roster × `lifelineOnDutyRatio`

標準`lifelineOnDutyRatio=0.30`。

## 7. Industrial logistics

Supply stage:

```text
source outputStage 0 → processor inputStage 0
processor outputStage 1 → assembler inputStage 1
assembler outputStage 2 → retail/export
```

General truck constants:

```text
capacity = 240
LOAD_SECONDS = 5
UNLOAD_SECONDS = 6
fleetSize = clamp(ceil(siteCount / 3.5), 18, 72)
```

Production site update中だけ`processRate = baseRate * workplace efficiency`へ差し替え、update後にbase rateへ戻す。

## 8. Thermal fuel

Thermal inventoryはactual generationに応じて消費する。

標準:

```text
0.18 units/MWh
storage 96 h equivalent
initial stock 80%
reorder 60 h
emergency 18 h
truck 180 units
fleet 10
internal raw-factory reserve 25%
```

Fuel availability factorは、次のdispatch intervalを賄えるstockがある間は1。ほぼ空の時だけ連続的に低下し、0 stockで0になる。

`reservedInbound`をreorder判定へ含め、同じ不足に対する重複dispatchを抑制する。

## 9. Lifeline fuel truck integration

Fuel source priority:

1. raw-factory surplus while preserving configured reserve;
2. city gate import.

Fuel truck phaseは一般物流と独立APIを持つ。VehicleStoreではtruckとして通常trafficへ参加し、unload完了時だけplant stockを増やす。

## 10. Power delivery

### 10.1 Path capacity tuning

`PowerGridCapacityTuning`はsource feeder、station-adjacent path、consumer distribution path等のrating floorを調整する。過去updateで恒久的に積み上がらないようbase ratingへ戻してから必要floorを適用する。

### 10.2 Reliable delivery

`PowerDeliveryTuning`が`PowerSystem.distributePower()`をwrap/replaceする。

Hard checks:

```text
consumer has substation
substation online + source + same zone
all path segments active
zone available source capacity
```

Flow allocation:

```text
deliverable = min(consumer demand, zone remaining capacity)
```

Priority order:

```text
Critical → High → Medium → Low
```

Flowを割り当てた後に:

```text
substation.overload = supplied or demand > rating
line.overload = actual currentLoad > rating
```

を評価する。Rating自体でhealthy consumer供給を即時clipしない。

Generation dispatchはdistribution後に行う。Snapshot reserveは利用可能なinternal generation + external maxImportと需要の差を基礎にするため、「市内発電だけの余力」ではない。

## 11. Power facility binding / rendering

Power integrationは`PowerFacilityBuildingBinding`でasset keyとBuilding IDを対応させる。

地上facility visualは`PowerFacilityBuildingVisualTuning`が通常`EnhancedRenderer` Building描画へ追加detailを載せる。

- thermal: facility color + stacks
- solar: facility color + panel rows
- substation/external: facility color + transformer/switchgear

電線・電柱は追加しない。

Inspectorは`infrastructureLabel`/roleを先頭に追加する。

## 12. Power jump

`PowerFacilityJumpTuning`はpower UI rowからlogical snapshot x/zへ直接飛ばず、power key → binding → `buildingId` → actual Buildingを解決する。

CameraはBuilding frontage側へ配置し、Building centerを向く。Menu closeは正式なmenu toggle pathを使い、内部open stateを残さない。

## 13. Multi-lane / turn

`MultiLaneTrafficTuning`がlane runtimeをside dataとして持つ。

`TurningLaneTransitionFix`はturn laneとdownstream lane-count mergeの矛盾を回避し、real `RoadEdge.lanes`を恒久変更しない。

`TurningVisualPathTuning`はbase logical update後にvisual zoneだけposition/headingを補正する。

## 14. Pedestrian crossing

`PedestrianCrossingSafetyTuning`はcrossing occupancy/conflictを維持する。

`PedestrianSignalWaitTuning`はblocked crossingで約1.15 m手前まで接近し、path/pathCursorを保持してvelocity 0で待つ。

## 15. Bus / Taxi

Short bus constants:

```text
MAX_ROUTE_METERS = 5000
TARGET_ROUTE_METERS = 4600
```

Taxi targetは概ね`population / 800`を18～120へclampし、vehicle availabilityにも制約される。

## 16. F10 menu / analytics

Base `FullScreenMenuTuning`はBuildings/Cars/Buses/Taxis/Trains/Graphicsを持つ。Runtime extensionでTruckとPowerを追加する。

`FullScreenMenuAnalyticsTuning`:

```text
HISTORY_INTERVAL_SIM_SECONDS = 60
HISTORY_LIMIT = 120
```

ChartはSVG/CSS。Power seriesはdemand/supply/internal/external。建物/vehicle系はbar chart。

`FullScreenMenuInteractionTuning`はTruck panelを追加し、Train statusの速度付き文字列を正規化してcategory explosionを防ぐ。

## 17. CI / performance

CI standard:

```text
npm ci
npm run build
npm run bench:power
verify dist/LICENSE
verify dist/NOTICE
verify dist/THIRD_PARTY_NOTICES.txt
```

Power P12 benchmarkはhot-path regression detectorであり、ゲーム全体FPSの倍率を保証するものではない。

## 18. 変更時チェック

### Generation

- reserved Building conflict
- POI disable/recreate
- Building ID stability
- frontage/road access
- facility/production/depot registry consistency

### Workplace/lifeline

- present vs onDuty semantics
- shift rollover
- startup/handover grace
- roster target vs concurrent target
- power operational factor

### Power

- topology connectivity
- zone available capacity
- rating diagnostics vs hard constraints
- generation dispatch order
- fuel inventory/reserved inbound
- Building binding/jump/Inspector

### UI

- menu open/close internal state
- search/paging
- analytics duplication after DOM refresh
- jump target resolution
- hard reload/HMR patch stacking

### Rail/Traffic

- logical path/stateとvisual correctionの分離
- signal/pedestrian/lane invariants
